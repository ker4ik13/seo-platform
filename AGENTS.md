# Правила работы с проектом

## Обязательный контекст

Перед любым изменением:

1. прочитать `PROJECT_MAP.md`;
2. открыть релевантный раздел `docs/technical-spec/00-index.md`;
3. проверить существующий код и зависимости затрагиваемого сервиса;
4. не менять границы владения данными без ADR.

После изменения структуры, нового модуля, сервиса, очереди, таблицы, события или инфраструктурного компонента обновить `PROJECT_MAP.md`.

## Инженерные правила

- Следовать SOLID, KISS, DRY и Clean Architecture без формального усложнения.
- Один модуль имеет одну доменную ответственность.
- Не обращаться напрямую к БД другого сервиса.
- Не дублировать API/event types: общие контракты находятся в `packages/contracts`.
- Не помещать секреты в код, Git, URL, логи, события и queue payload.
- Долгие и внешние операции выполняются асинхронно.
- Платные команды идемпотентны и используют estimate/reservation/settlement.
- WebSocket не является источником истины.
- Все tenant-запросы требуют проверенного workspace/project context.
- Новая production-зависимость требует понятного обоснования.
- Не добавлять framework или abstraction до появления реального повторения.

## Качество

Для затронутого сервиса выполнить:

- `pnpm typecheck`;
- `pnpm lint`;
- `pnpm test`;
- `pnpm build`, если меняется production path.

Для Prisma:

- `pnpm prisma:validate`;
- `pnpm prisma:generate`;
- migration review.

Перед завершением:

- проверить loading/empty/error/degraded states;
- проверить permission boundary;
- проверить логи на секреты;
- проверить `PROJECT_MAP.md`;
- кратко описать способ проверки.
