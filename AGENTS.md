# Правила работы с проектом

## Обязательный контекст

Перед любым изменением:

1. прочитать `PROJECT_MAP.md`;
2. открыть релевантный раздел `docs/technical-spec/00-index.md`;
3. проверить существующий код и зависимости затрагиваемого сервиса;
4. не менять границы владения данными без ADR.

При расследовании production-ошибок дополнительно читать последние 15 дней
`platform_db.operational_error_events` только на чтение и сопоставлять записи с
логами/метриками; отсутствие записи не доказывает отсутствие ошибки при сбое БД.

После изменения структуры, нового модуля, сервиса, очереди, таблицы, события или инфраструктурного компонента обновить `PROJECT_MAP.md`.

## Инженерные правила

- Следовать SOLID, KISS, DRY и Clean Architecture без формального усложнения.
- Один модуль имеет одну доменную ответственность.
- Не обращаться напрямую к БД другого сервиса.
- Не дублировать API/event types: общие контракты находятся в `packages/contracts`.
- Не помещать секреты в код, Git, URL, логи, события и queue payload.
- Долгие и внешние операции выполняются асинхронно.
- Платные команды идемпотентны и используют estimate/reservation/settlement.
- WebSocket не является источником истины.
- Все tenant-запросы требуют проверенного workspace/project context.
- Новая production-зависимость требует понятного обоснования.
- Не добавлять framework или abstraction до появления реального повторения.

## Сквозная целостность продукта

- Серверное изменение, исправление или новый режим не считается завершённым,
  пока он не проведён через весь пользовательский путь: shared contracts,
  внутренние и публичные parsers/allowlists, BFF/browser client, UI controls и
  loading/empty/error/success states.
- При изменении server response или command shape найти и обновить все строгие
  consumers этого контракта. Нельзя ограничиваться producer-тестом или
  серверным unit-тестом, если действие запускается из интерфейса.
- Для изменённого пользовательского flow обязательно проверить реальный путь
  `UI → public API → owning service/worker → persisted result → UI` на
  production-like runtime через HTTPS. Для платного flow сначала выполнить
  бесплатную подготовку и расчёт максимальной стоимости, затем запускать
  только явно разрешённый bounded smoke.
- Любой новый backend default должен быть виден и управляем в UI там, где
  пользователь ожидает его настроить; UI default и серверный default должны
  совпадать и сохраняться после reload.
- Регрессионный тест должен пересекать границу, на которой менялся контракт:
  минимум producer + strict consumer, а для UI-функции также browser/E2E.

## Качество

Для затронутого сервиса выполнить:

- `pnpm typecheck`;
- `pnpm lint`;
- `pnpm test`;
- `pnpm build`, если меняется production path.

Для Prisma:

- `pnpm prisma:validate`;
- `pnpm prisma:generate`;
- migration review.

Перед завершением:

- проверить loading/empty/error/degraded states;
- проверить permission boundary;
- проверить логи на секреты;
- проверить `PROJECT_MAP.md`;
- кратко описать способ проверки.

## Локальный запуск

- Production-like runtime всегда запускать штатными скриптами из
  `infrastructure/vps`, с системным Caddy как единственной пользовательской
  точкой входа.
- Открывать и проверять Web только по HTTPS-адресу `SEO_PLATFORM_PUBLIC_URL`,
  который проксируется Caddy. Прямые loopback-порты сервисов, включая
  `127.0.0.1:3000`, допустимы только для readiness и диагностики.
- После запуска обязательно проверить `infrastructure/vps/status-runtime.sh`
  и пользовательский HTTPS-маршрут через Caddy.
