# MVP-аудит SEO Platform — 2026-08-27, обновлён 2026-08-31

## 1. Итог

Локально проверяемый MVP-контур доведён до состояния, в котором обязательные
typecheck, lint, unit/integration tests, production build, Prisma validation и
production dependency audit проходят. Реализованы внутренние токены,
reservation/capture/release для оплачиваемых provider-команд, platform-paid
Arsenkin/XMLStock и централизованные redacted Telegram alerts.

Статус релиза — **условный GO**: кодовый контур готов к staging, но production
включение платежей, Telegram, SMTP и provider API требует внешних credentials,
лимитов и canary-проверок из раздела 8. Эти проверки нельзя достоверно заменить
fixtures или моками.

Это инженерный security-аудит и попытка сломать доступные локальные границы,
но не независимый сертифицированный penetration test.

## 3. Внутренние токены и оплата provider usage

Источник истины находится в Core API:

1. Estimate создаётся сервером и фиксирует provider, workload, quantity,
   unit price и request hash.
2. Grant создаёт immutable usage reservation и balanced double-entry ledger
   transaction.
3. Перед первым платным HTTP connector читает exact settlement identity через
   ограниченную PostgreSQL-функцию и вызывает `HOLD` в Core.
4. Только после подтверждённого `ACCEPTED` provider outcome выполняется
   идемпотентный `CAPTURE`.
5. Неиспользованный или истёкший резерв возвращается через `RELEASE`.

BYOK не списывает внутренние токены и возвращает `NOT_APPLICABLE`. Terminal
reservation immutable; повтор с тем же economic scope идемпотентен, а drift
tenant/provider/quantity/price/request hash отклоняется.

Arsenkin и XMLStock доступны в двух режимах:

- `BYOK_API_KEY` — ключ workspace, без списания внутренних токенов;
- `PLATFORM_PAID` — system credential connector worker и списание по
  server-side pricebook.

Provider feature flags по умолчанию выключены. Включать их следует только
после canary и настройки обязательных hard request/spend limits.

Core требует `PLATFORM_*_DAILY_SPEND_LIMIT_MINOR` и
`PLATFORM_*_MONTHLY_SPEND_LIMIT_MINOR`. Лимит общий для provider между всеми
workspace и replicas: PostgreSQL сериализует новые reservations, считает
captured usage текущего UTC-окна вместе с живыми reservations и возвращает
`EXHAUSTED` до ledger mutation, если следующий платный item превышает cap.

Operator-owned pools задаются через `PLATFORM_XMLSTOCK_API_KEYS`,
`PLATFORM_XMLSTOCK_ACCOUNT_IDS` и `PLATFORM_ARSENKIN_API_KEYS`. Выбранный
физический ключ закреплён за асинхронным execution, а лимиты считаются по его
непрозрачному HMAC UUID, поэтому replicas и разные workspace не создают
отдельные окна для одного provider key.

## 4. Скрытые ошибки и Telegram

Добавлен отдельный private operational-alert receiver:

- принимает только exact versioned envelope по dedicated bearer token;
- не принимает stack trace, request body, headers, URL query, email, provider
  payload или credentials;
- выполняет bounded deduplication и rate limiting;
- отправляет Telegram только из receiver process, поэтому bot token/chat ID не
  распространяются по сервисам;
- supervisor преобразует stderr error-like события в SHA-256 fingerprint и
  bounded metadata;
- uncaught exception/unhandled rejection и worker terminal failures попадают
  в единый канал;
- при недоступности Telegram приложение продолжает работать, а alert transport
  остаётся degraded и наблюдаемым.

Runbook: `infrastructure/runbooks/operational-alerts.md`.

## 5. Security-проверки

- нет вызовов Prisma `$queryRawUnsafe`/`$executeRawUnsafe`;
- Redis `EVAL` использует только статический Lua, без сборки скрипта из input;
- единственный `dangerouslySetInnerHTML` — JSON-LD после escaping;
- не найдено логирование secret/token/password/ciphertext/provider material;
- не найдено незакрытых `TODO/FIXME/HACK/XXX` в production path;
- service tokens проверяются на placeholder, длину, попарную уникальность и
  process audience;
- PostgreSQL roles — `NOINHERIT`, без superuser/createdb/createrole/bypassrls;
- connector не имеет direct table/sequence DML и получает exact routine
  allowlist;
- auth-email worker имеет только `SELECT/INSERT/UPDATE` одной redacted таблицы;
- tenant scope и workspace/project context повторно проверяются на HTTP, DB и
  provider authorization boundaries;
- `pnpm audit --prod`: известных production vulnerabilities нет.

## 8. Обязательные внешние release-gates

1. **Telegram canary:** установить реальный bot token/chat ID, выполнить
   redacted test alert, проверить dedupe/rate limit и degraded recovery.
2. **YooKassa:** sandbox payment, signed webhook replay, duplicate delivery,
   partial/full refund и reconciliation с реальным shop credential.
3. **Arsenkin/XMLStock:** юридически разрешённые ключи, по одному минимальному
   BYOK и platform-paid запросу, provider balance alert, hard daily spend cap,
   timeout/rate-limit/ambiguous-response fault injection.
4. **SMTP:** verification/reset/invite canary, bounce/DLQ и отсутствие
   recipient/token/content в durable logs/storage.
5. **Target infrastructure:** `docker compose config` в фактической версии
   Dokploy, deploy/rollback, backup restore/PITR rehearsal и alert on-call.
6. **Distributed settlement window:** если provider уже принял запрос, а Core
   CAPTURE временно недоступен, пользователь не списывается и local outcome не
   финализируется, но platform cost уже возможен. Перед production включением
   требуется provider-specific idempotency canary и fault injection; при
   отсутствии надёжной provider deduplication нужен отдельный durable
   `CAPTURE_PENDING` recovery design через ADR.
7. **Legal/security:** Terms/Privacy/DPA, tax/invoice flow, admin MFA и
   независимый penetration test должны быть закрыты либо явно приняты как
   release risk.

До прохождения этих gates не следует включать production provider/payment
flags, даже если локальный CI полностью зелёный.
