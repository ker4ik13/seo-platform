# ADR-2026-057: пакетная продуктовая аналитика

Дата: 8 октября 2026 года. Статус: принято, локальная реализация.

## Контекст

Активность по `sessions.last_used_at` включает фоновые запросы и не хранит
историю работы по дням. В SaaS с расписаниями необходимо различать людей,
команды и автоматические операции. Аналитика не должна сканировать семантику,
Job items и provider payload при каждом открытии графика.

## Решение

Core API владеет `ProductAnalyticsModule` и таблицами `product_analytics_*`.
Авторизованный браузер отправляет ограниченные пачки максимум раз в минуту
при непрерывной работе и при смене экрана. Body содержит только типизированные
события, времена, enum-разделы и проверяемые workspace/project IDs. Идентификатор
пользователя устанавливается из сессии; CSRF и tenant authorization обязательны.
Валидация запрещает произвольные properties, тексты запросов, URL, личные данные
и события о деньгах. Ротация access session не меняет продуктовую сессию.

Секундные bitmap объединяются по user/minute внутри одной транзакции с
advisory lock на пользователя. Общая длительность — объединение интервалов
вкладок/устройств, длительность разделов — отдельная атрибуция. Браузерные
измерения приблизительны и не используются для биллинга. Receipts делают
повтор пачки идемпотентным. Подробные bitmap/receipts хранятся 48 часов при
максимальном возрасте входного события 24 часа; суточные агрегаты — 400 дней,
продуктовые сессии — 90 дней. Очистка каждые 5 минут ограничена пачками по
10 000 строк, десятью проходами и мягким бюджетом 2 секунды; отдельные SQL
имеют timeout 1 секунду. Повторный проход нужен только при накопленном хвосте.
Счётчики не дублируются в гистограммах; timing-only события не создают пустые
суточные срезы, неизменившийся профиль не обновляется.

Execution владеет `operation_analytics_facts`. Триггеры записывают небольшую
проекцию при создании задания, смене статуса, первом положительном прогрессе
и финансовом завершении; per-keyword updates и provider responses не копируются.
Отдельный триггер учитывает импорт. Начальный backfill берёт метаданные последних
90 дней; неизвестное историческое время первого результата остаётся NULL.
Применение backfill на крупной production базе требует измерения миграции
на representative копии перед публикацией.

Админка получает отчёт Core, который читает свои агрегаты и проверяет строгий
ответ Execution по существующему внутреннему API. Чужие БД напрямую не
читаются. Отчёты single-flight кешируются на 5 минут по периоду, сегменту и
финансовым правам; UI опрашивает их не чаще минуты. Activity-report выполняется
в согласованном read snapshot со statement timeout; отчёт Execution также
ограничен timeout. Никаких новых deployables,
SDK или production-зависимостей не добавляется. Новые SQL routines получают
точечные grants в существующем permission provisioner.

## Метрики и определения

- DAU/WAU/MAU: уникальные люди с 30 секундами активного времени либо действием/
  просмотром существующего результата; календарные UTC-дни, последние 7/30
  дней. Эти distinct counts не суммируются между днями.
- После 2 минут без взаимодействия, в скрытой вкладке и без focus время не
  начисляется; новая продуктовая сессия начинается после 30 минут простоя.
- D1/D7/D30 отсчитываются от первого активного дня; в знаменателе только
  созревшие когорты. Недельные периоды также не показывают незрелые проценты.
- Активация новых аккаунтов проверяется по одному registration cohort, а не
  делением несвязанных событий одного периода. Первый просмотр результата
  имеет отдельный timestamp.
- Запуски по расписанию и пользователь/API-запуски разделены в Execution;
  автоматическое завершение никогда не создаёт активного пользователя.
- Первое открытие пустой карточки не считается просмотром результата.
- Автоматическое сохранение настроек, чтения/preview/estimate и фоновые
  presence-запросы не считаются пользовательским действием.
- Browser API/interaction p95 — приблизительный quantile по фиксированным
  диапазонам. Это не полная серверная SLO-телеметрия; interaction timing не
  выдаётся за точное INP.
- Поступления/возвраты берутся из подтверждённого биллинга. BYOK provider
  cost не считается выручкой платформы.

## Доступ и ограничения

Аналитика доступна только MFA-backed platform staff ролям ANALYST, OPERATIONS,
SUPPORT, FINANCE и SUPER_ADMIN. Финансы возвращаются только FINANCE/SUPER_ADMIN;
это отдельный ключ кеша. По умолчанию исключены сотрудники и example.invalid
fixtures, переключатель сегмента и период сохранены в URL. Внутренние ошибки
из 15-дневного журнала показываются безопасными агрегатами всей платформы.

Историю активного времени до внедрения восстановить нельзя. Графики показывают
границу покрытия. Кеш не превращает неизвестное состояние owning service в
ноль: источник помечается недоступным. При дальнейшем росте число/длительность
аналитических запросов измеряются отдельно; отдельная схема на том же сервере
PostgreSQL сама по себе не изолирует CPU. Вынос хранилища определяется нагрузкой,
а не наличием аналитического раздела.

## Проверка

Реальная PostgreSQL проверка: пересечение двух вкладок, идемпотентные receipts,
tenant context, canonical job/import projections и role grants. Browser E2E:
реальный CSV import, просмотр сохранённой частотности, активность через HTTPS
BFF, отчёт и графики, ANALYST без финансов, SUPER_ADMIN с финансовыми данными,
повторные чтения одного cached report и сохранение фильтров после reload.
Все вкладки и CSV-выгрузка также проверены браузером. Тестовые роли и сессии
после smoke отзываются с аудитом.

Изолированная PostgreSQL 18, 8 октября: 1000 пользователей, 90 000 суточных
scope facts — activity report 570 мс; 1000 настоящих вызовов ingest с
конкурентностью 4 — 3528 мс. Это synthetic workload на локальном стенде,
не гарантия production capacity. Production baseline CPU/IOPS и backfill
проверяются отдельно перед будущей публикацией.
