# ADR-2026-049: постоянная проекция истории позиций проекта

Статус: реализовано, 15 сентября 2026 года.

## Причина

Главный график позиций вычислял до 100 дневных точек непосредственно из всего
append-only `rank_snapshots`. После импорта 802 087 снимков один холодный запрос
занимал около 12 секунд. Несколько открытых вкладок повторяли одинаковую
агрегацию, создавали лишнюю нагрузку и могли упереться в transport timeout.

Обычный TTL-cache недостаточен: после завершённого съёма, импорта, изменения
`isTracked`, архивации контекста, удаления истории или объединения срезов нельзя
показывать старые показатели до истечения времени.

## Решение

- Владельцем остаётся Core SEO и `seo_db`. Межсервисная граница и исходные
  append-only snapshots не меняются.
- `project_position_history_revisions` хранит монотонную project revision.
  Statement-level transition-table triggers увеличивают её один раз на SQL
  statement, затрагивающий rank snapshots или семантику проекции. Число строк в
  импортном chunk не увеличивает число служебных update.
- `project_position_history_projections` хранит bounded JSON результата,
  `scope_hash`, версию алгоритма и exact source revision. Scope включает режим
  tracked/all-active и необязательный canonical rank dimension.
- Read сначала сравнивает revision по первичному ключу. Совпадающая проекция
  отдаётся без сканирования истории. Missing, повреждённая или stale строка
  пересчитывается; revision проверяется до и после расчёта. Изменение данных во
  время расчёта заставляет выполнить его ещё раз и не маркирует старый payload
  свежим.
- Одновременные одинаковые запросы внутри SEO процесса объединяются в один
  rebuild. После успешной rank finalization и завершения semantic import
  default tracked-проекция прогревается асинхронно; ошибка прогрева не влияет на
  authoritative write и исправляется следующим read.
- Обе таблицы tenant-scoped и входят в существующий перенос проекта между
  workspace. Provider payload, keyword text и credential data в них не
  сохраняются.

## Последствия

Первое чтение старого проекта или нового dimension может выполнить один полный
расчёт. Все следующие чтения до изменения revision используют постоянную
проекцию, включая чтения после рестарта процесса. Любая новая причина изменения
графика обязана войти в revision trigger до выпуска соответствующей функции.

## Приёмка

- миграция проверяет bounded JSON, положительную revision и tenant key;
- unit-тест подтверждает cache hit и rebuild после смены revision;
- PostgreSQL-проверка подтверждает один bump на statement и перенос обеих
  таблиц вместе с проектом;
- на импортированном проекте первый расчёт и повторный HTTPS-read сравниваются
  по payload, revision, длительности и отсутствию 5xx.
