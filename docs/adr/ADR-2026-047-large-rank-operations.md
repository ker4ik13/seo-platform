# ADR-2026-047: большие операции съёма позиций

Статус: реализовано и проверено на 50k в PostgreSQL, 7 сентября 2026.

## Причина

Владелец требует комфортной работы с 50 000 ключей и запасом роста. Старый
контур Arsenkin v2 ограничивает всю команду одним provider task на 15 000,
а XMLStock v1 ограничен тем же общим числом. На тарифе Standard Arsenkin
даже 15 000 не принимаются одной задачей: опубликованный предел — 5 000.
Увеличивать только frontend limit или переопределять старую sealed policy нельзя.

## Решение

- Сохраняются неизменяемые политики Arsenkin v1 (1 000 / chunks 250),
  Arsenkin v2 (15 000 / один chunk) и XMLStock v1 (15 000 / chunks 1).
- Новые политики Arsenkin v3 и XMLStock v2 допускают до 300 000 ключей
  в одной операции. Arsenkin получает пакеты не более 5 000, совместимые с
  опубликованным Standard API; XMLStock по-прежнему работает по одному запросу.
- Provider task count и максимальная цена всей операции видны в estimate.
  Rank резервирует деньги по отдельным provider tasks; факт принятия и деньги
  отслеживаются по каждой независимой отправке.
- Shared contracts описывают версии и shape. Исторические hashes, manifests,
  reservations и snapshots не переписываются. Новый seal явно связывает
  выбранную policy; отсутствие нового поля сохраняет legacy поведение.
- Обработка и сохранение пакетов ограничены по размеру. Проверка content bytes
  происходит до материализации текстов; общий cap не означает разрешение
  создавать один безграничный JSON/SQL insert.
- Старые overflow sentinels 1 001 / 15 001 нельзя интерпретировать как
  превышение лимита новой policy: для неё это обычное количество ключей.

Владение данными не меняется: Core API — полномочия и деньги; Execution —
операция, provider tasks и tickets; SEO — assignments, manifests и результаты.
Новые очереди, deployment-компоненты и внешние SDK не требуются.

## Ограничения

Кластеризация не является независимым съёмом по каждому ключу: разбиение
на произвольные пакеты меняет общий результат. Для неё нельзя выдавать
локальную склейку за полный Arsenkin clustering. Опубликованные пределы
Arsenkin: Standard 30 000, Corporate 70 000; они должны быть видны до запуска.
Проект может быть больше и обрабатываться по осмысленно выбранным папкам.

Источник: [тарифы и ограничения Arsenkin](https://arsenkin.ru/tools/tariffs/all/),
проверено 7 сентября 2026. API доступен на Standard/Corporate. Их лимиты могут
меняться; transport остаётся обязанным принимать подтверждённые provider errors.

## Приёмка

Реальный изолированный PostgreSQL: 50 000 назначений и sealed entries,
границы chunks, сумма progress, роли connector, idempotency и финализация.
Проверить 1 001 / 15 001 как обычные valid counts новой policy и сохранность
  legacy replay. Нагрузка чтения/поиска/экспорта — через HTTPS/Caddy.
Полные provider-запуски на 50k выполняются controlled transport; живые платные
canary остаются в ранее согласованном пределе **5 requests / 5 keywords**.

## Совместимость переключателя выполнения

Батчинг использует тот же wire protocol провайдера и меньший физический пакет.
В SQL явно перечислены пары допустимых batching/wire policy: контроль Arsenkin
v2 допускает v3, контроль XMLStock v1 допускает v2; новые control versions могут
дорабатывать ранее sealed совместимые policies. Поля submit_enabled, connector
version, credential validation, lease и точное совпадение kill-switch generation
остаются обязательными. Сама active control row не меняется: её изменение
обязательно создало бы новую generation и отозвало допуск уже начатых операций.
Исторические строки control_versions и job evidence не переписываются.
