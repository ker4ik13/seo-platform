# ADR-2026-037: единый GitHub-репозиторий для переноса разработки

- Статус: принято
- Дата: 29 июля 2026 года
- Затронутые области: source control, CI/CD, Dokploy deployment
- Изменение API/БД: отсутствует

## Контекст

Изначально локальный workspace координировал несколько самостоятельных
Git-репозиториев `platform-*`. Такая схема сохраняла возможность независимого
выделения команд и релизов, но усложняла перенос всей разработки на удалённый
сервер: корневой репозиторий не содержал исходный код сервисов, а отдельные
remote URL ещё не были назначены.

Для продолжения разработки на VPS нужен один канонический GitHub-клон, который
содержит ТЗ, инфраструктуру и весь исходный код без локальных ссылок и
неинициализированных submodules.

## Решение

Каноническим source repository становится один GitHub monorepo. Каталоги
`platform-*` импортируются в корневую историю как обычные отслеживаемые
директории с сохранением существующих Git-коммитов через несжатый
`git subtree`.

При этом не меняются runtime-границы:

- backend-сервисы по-прежнему владеют отдельными PostgreSQL databases;
- deployable-компоненты собираются и масштабируются независимо;
- прямой доступ к БД другого сервиса запрещён;
- общие API/event contracts остаются в `platform-contracts`;
- отдельные worker entrypoints остаются самостоятельными Dokploy processes.

После консолидации новые изменения коммитятся в корневом репозитории. Если
позже появится операционная необходимость снова выделить сервис, его историю
можно получить через `git subtree split`.

## Последствия

Положительные:

- один `git clone` восстанавливает весь проект;
- межсервисные изменения contracts/producer/consumer можно проверять одним CI;
- root lockfile, ТЗ и код не расходятся между remote-репозиториями;
- Dokploy получает единый build context.

Ограничения:

- независимые права доступа и release cadence на уровне Git-репозиториев пока
  отсутствуют;
- CI обязан сохранять package/service-level проверки, чтобы monorepo не
  размывал доменные границы;
- большой межсервисный commit допустим только для одного связного
  вертикального среза.

## План миграции

1. Завершить и отдельно зафиксировать текущие изменения в каждом локальном
   репозитории.
2. Создать локальные recovery bundles исходных Git-историй.
3. Импортировать каждый `platform-*` каталог без `--squash`.
4. Удалить исключения `platform-*` из корневого `.gitignore`.
5. Проверить отсутствие секретов и чрезмерно больших blobs.
6. Выполнить workspace QA и отправить ветку `main` в канонический remote.

Откат до push: восстановить корневую ветку и локальные репозитории из recovery
bundles. После push исходные коммиты остаются достижимыми из истории monorepo.
