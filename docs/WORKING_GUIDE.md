# Как работать с SEOньоритой

Обновлено 7 сентября 2026 года. Это практическая инструкция для владельца и
разработчика; целевые требования остаются в техническом задании.

## С чего начинать новую задачу

1. Прочитать `AGENTS.md`, `PROJECT_MAP.md` и нужный раздел
   `docs/technical-spec/00-index.md`.
2. Проверить `git status --short`: не перезаписывать чужую незавершённую работу.
3. Найти владельца данных по карте. Auth/workspace/project/billing — Core API;
   семантика/позиции/заметки/страницы — Core SEO; Jobs/uploads/provider vault —
   Execution; уведомления/Web Push — Realtime. Прямые запросы приложения в
   чужую БД запрещены. Общие HTTP/event types — в `packages/contracts`.
4. Читать код вместе с тестами, схемой и последними миграциями. Запись в
   roadmap — требование, а не доказательство готовой функции.
5. Изменения владения данными требуют ADR. Новый файл или эксплуатационный
   механизм нужно отразить в карте; существенный долг — в MVP checklist.

## Инструменты и проверки

Node.js 24+, pnpm 11.17.0. Установку делать через `pnpm install --frozen-lockfile`.
Не смешивать npm/yarn lockfiles. Production зависимости добавлять только с
объяснением необходимости. После изменения:

```bash
pnpm prisma:validate
pnpm prisma:generate
pnpm typecheck
pnpm lint
pnpm test
pnpm audit --prod
pnpm build
```

Для небольшой задачи допустим `pnpm --filter @seo-platform/frontend test` и
соответствующий сервисный typecheck; общий lint остаётся корневой командой.
Если меняется production path, сборка обязательна. Prisma generate/validate
не применяют миграции; SQL review и реальный PostgreSQL test — отдельные шаги.

Обычный `pnpm test` **пропускает** некоторые тесты реальной БД и Redis, если не
заданы их opt-in переменные. Наличие зелёного unit-suite не подтверждает
изоляцию PostgreSQL, работу Caddy, загрузку файла или оплату.

## Локальный runtime

Канонический адрес берётся из `SEO_PLATFORM_PUBLIC_URL` в защищённом
`/home/dev/.local/share/seo-platform-runtime/runtime.env`. Текущее окружение:
`https://144.31.221.28:3000`. Это HTTPS listener системного Caddy; браузер не
должен открывать `http://127.0.0.1:3000`.

```bash
infrastructure/vps/status-runtime.sh
infrastructure/vps/backup-runtime.sh
infrastructure/vps/stop-runtime.sh
infrastructure/vps/build-runtime.sh
infrastructure/vps/start-runtime.sh
infrastructure/vps/status-runtime.sh
```

Для сборки Web нужны несекретные `WEB_PUBLIC_URL` и `API_PUBLIC_URL` из
конфигурации этого runtime. Не собирать `.next` поверх работающего Web: он
может начать отдавать смесь старых и новых chunks. Секреты не передавать
в аргументах CLI, не печатать `runtime.env`, `env`, signed URL или cookie jar.
`start-runtime.sh` применяет штатные миграции и ACL, ожидает readiness зависимостей.
Остановка действует только на tmux-сессию SEO Platform.

После старта проверить публичную страницу и важный авторизованный сценарий
через Caddy. Loopback readiness достаточна только для диагностики.
`status-runtime.sh` теперь возвращает ненулевой exit code при недоступном
компоненте, проблеме публичного HTTPS или нехватке места.

## Сквозные тесты

Команды создают **отдельные синтетические** аккаунты и проекты. Они не
используют существующие BYOK-ключи и не выполняют платёж или платный provider call.

```bash
SEO_PLATFORM_SMOKE_CONFIRM=CREATE_TEST_DATA \
SEO_PLATFORM_SMOKE_STORAGE_RELAY=true infrastructure/vps/smoke-runtime.sh

SEO_PLATFORM_API_SMOKE_CONFIRM=CREATE_TEST_DATA \
  infrastructure/vps/smoke-public-api.sh

pnpm exec playwright install chromium
SEO_PLATFORM_E2E_CONFIRM=CREATE_TEST_DATA \
  infrastructure/vps/test-browser.sh
```

Если на минимальном VPS нет системных библиотек Chromium, установить их
штатным способом либо передать `SEO_PLATFORM_BROWSER_LIBRARIES` с каталогом
уже установленных библиотек. На текущем сервере используется
`/home/dev/.local/playwright-libs/usr/lib/x86_64-linux-gnu`.
Скриншоты и JSON отчёт сохраняются в напечатанный каталог `runtime/tmp/e2e.*`.
При повторной работе сохранять только нужные артефакты: через 7 дней этот
управляемый временный каталог может удалить обслуживание.

API smoke проверяет personal tokens, scopes, project allowlist, rotation,
revoke и cross-tenant доступ. Runtime smoke проверяет настоящий crawl, S3,
ClamAV, импорт, публикацию, обработку дублей и XLSX export. Browser suite
проверяет реальные записи, concurrency/CSRF, публикацию и отзыв заметки,
14 экранов настроек на четырёх ширинах, сохранение и восстановление после ошибки.
Fault injection ответа 503 в браузере — отдельная проверка состояния ошибки,
остальные успешные ответы идут от локальных сервисов.

Готовый runner сам создаёт такой кластер, генерирует временные пароли,
применяет миграции, запускает проверки и останавливает только свой процесс:

```bash
SEO_PLATFORM_POSTGRES_TEST_CONFIRM=CREATE_ISOLATED_CLUSTER \
  infrastructure/vps/test-postgres.sh
```

Для PostgreSQL concurrency/ACL тестов нужен **одноразовый кластер на другом
порту**, не рабочие БД! В частности,
`service-database-role-isolation-postgres.test.mjs` создаёт и удаляет
`platform_db`, `seo_db`, `jobs_db`, `realtime_db`. Никогда не направлять его на
runtime 5432. Имена opt-in переменных и фактические результаты приведены в
аудите `mvp-audit-2026-09-06.md`.

## Теги запросов

При добавлении и одиночном редактировании выберите тег в поисковом списке
либо введите новое название и нажмите Enter. Запятая — часть названия одного
тега. Крестик убирает конкретный чип; изменение сохраняется вместе с формой.

Массовая форма содержит два независимых блока: «Добавить теги» присоединяет
указанные теги ко всем выбранным запросам; «Снять теги» снимает только явно
указанные теги. Крестик в этих блоках отменяет соответствующее действие до
нажатия «Применить». Остальные теги каждого запроса сохраняются. Один тег
нельзя одновременно добавить и снять: последнее выбранное действие заменяет
противоположное. Снятие не удаляет тег из справочника проекта.

## Города, устройства и история позиций

В окне «Сбор позиций» или «Сбор конкурентов» добавьте города и включите для
каждого ПК, телефон либо оба устройства. Первый клик рассчитывает все отдельные
съёмы и показывает итоговый расход; следующий подтверждает запуск. Если вкладка
закрылась после принятия части задач, откройте то же окно и восстановите запуск:
сохранённые idempotency keys не позволят списать и отправить их повторно.

Колонки сравнения включаются в «Колонки и представления»: у каждого сочетания
поисковика, города и устройства есть позиция, URL и дата. Карточка запроса
позволяет выбрать тот же срез для графика, журнала позиций и истории выдачи.
В списке срезов логотип показывает поисковик, а значок — ПК или телефон;
увеличенная дельта рядом с позицией показывает рост или падение. Фильтр позиции
всегда использует последний замер выбранного среза.

Главный проектный график показывает дни. Если за UTC-день было несколько
съёмов, Core SEO оставляет для каждого запроса последний результат этого дня и
строит одну точку, поэтому повторные проверки не раздувают TOP-счётчики.

В проектных Markdown-заметках нет прежнего лимита 100 000 символов. Большой
текст сохраняется целиком в пределах общего допустимого размера HTTP-запроса.

Для переноса истории откройте «Экспорт → История позиций», выберите один
поисковик и период. Полученный XLSX можно загрузить обратно через «Импорт».
Мастер распознаёт режим автоматически. В таком файле пустая ячейка означает
«не снималось», а `-`, `–` и `—` — «снималось, но не найдено». Столбцы города,
устройства и языков из экспорта имеют приоритет над defaults. Не редактируйте
сводные строки `ТОП-N`: при импорте они пропускаются.

Без внешних запросов этот контур проверяется unit-тестом
`frontend/lib/rank-target-batch.test.ts`, round-trip тестом
`backend-execution/src/semantic-exports/semantic-export-encoder.test.ts` и
PostgreSQL-тестом
`backend-core/modules/seo/src/semantic-imports/manual-position-history-postgres.integration.test.ts`.

Сквозная проверка `infrastructure/e2e/tag-chips.test.mjs` использует настоящий
локальный API через Caddy и отдельные synthetic session fixtures. Проверяет
добавление/снятие чипов, запятые, лимит 50 тегов без обрезания прежних,
конфликт версий, чужой tenant, CSRF, retry поиска и RU/EN формы на ширинах
320/390/768/1440 px. Для запуска нужны `SEO_PLATFORM_E2E_CONFIRM=CREATE_TEST_DATA`,
канонический `SEO_PLATFORM_PUBLIC_URL`, защищённый `SEO_PLATFORM_SESSION_FIXTURES`
с двумя аккаунтами от `prepare-session-fixtures.mjs` и каталог
`SEO_PLATFORM_E2E_OUTPUT_DIR` внутри `runtime/tmp/e2e.*`. Сам тест:
`node --test infrastructure/e2e/tag-chips.test.mjs`. Файл сессий никогда не
публиковать; платных provider calls в этой проверке нет.

## Журналы, диск и ежедневное обслуживание

```bash
infrastructure/vps/maintain-runtime.sh --dry-run
infrastructure/vps/maintain-runtime.sh
infrastructure/vps/install-maintenance.sh
```

Установлен пользовательский cron: ежедневно **04:17 по времени сервера**.
Установка идемпотентна и сохраняет остальные cron jobs. Одновременные запуски
не пересекаются благодаря `flock`. Результат — компактная JSON-строка в
`runtime/logs/maintenance.log`.

- Supervisor постоянно ограничивает журнал: текущие 10 MiB и один предыдущий
  сегмент до 10 MiB. Старый слишком большой журнал сокращается до хвоста.
- Ежедневно удаляются только архивы журналов старше 14 дней и управляемые
  каталоги `smoke-runtime.*`, `smoke-public-api.*`, `e2e.*` в `runtime/tmp`
  старше 7 дней. Каталог живого PID пропускается, symlink не обходится.
- PostgreSQL, S3, пользовательские импорты, история позиций, ledger и backup
  не участвуют в файловой очистке. Для доменной retention нужен отдельный
  процесс владельца данных с согласованной политикой.
- Для Docker добавлено ограничение container logs: 10 MB × 3 файла.

При ошибке S3 507 сначала проверить диск, а не сбрасывать buckets или
перезапускать MinIO. Его readiness может оставаться 200 при отказе записи.
Не удалять PostgreSQL WAL/data, `node_modules`, активные build artifacts или
все `/tmp/*` одной командой. Сначала установить источник роста.

## Как безопасно менять интерфейс

Общий каркас настроек — `frontend/components/settings-tabs.tsx`; общий стиль —
`frontend/app/app/settings.css`, подключённый после legacy styles. Использовать
одинаковые headings, отступы, поля, actions и карточки. Не добавлять новые
локальные уменьшения текста до 8–10 px. `aria-busy` только объявляет состояние;
форма при сохранении не должна менять число колонок или прыгать по высоте.

Проверять 320/390/768/1440 px, длинные названия и email, клавиатуру, выбранный
раздел, отсутствие перекрытий, доступность кнопок внизу страницы. Отдельно
проверять loading, empty, error/retry, offline, read-only и отсутствие прав.
UUID, SQL/ledger-термины и внутренние названия компонентов нужны в документации
и диагностике, а не в обычных пояснениях к форме.

## Перед продажей подписок

Рабочая локальная демонстрация и готовность публичного платного сервиса — разные
статусы. Приёмка платежей требует доказательств настоящего checkout/webhook/
reconciliation/refund/receipt workflow, готовой почты, документов, поддержки,
backup и мониторинга. Конкретный порядок работ: `MVP_LAUNCH_CHECKLIST.md`.

## Финансовые операции и уведомления

Цены и ёмкость — `PRICING_AND_LIMITS.md`. Деньги хранятся в целых копейках,
provider себестоимость — в micro-RUB. Не принимать цены из браузера, не
повторять неопределённый платный запрос и не очищать зарезервированные суммы
вручную SQL-командой. В `/admin` → «Расходы на проверке» администратор
выбирает подтверждённое списание либо освобождение резерва. Для списания
нужен номер операции провайдера, для обоих решений — основание и подтверждение.

Для rank `provider_started_at` означает, что отправка могла состояться:
таймер такой резерв не освобождает. Старый worker/sweeper нельзя запускать
поверх новых финансовых записей. Последовательность rollback описана в
`adr/ADR-2026-048-rank-settlement-and-billing-notices.md`.

Финансовые письма используют существующие AUTH_EMAIL/SMTP env. Core создаёт
`billing_notices` и outbox, Execution получает адрес/материал непосредственно
перед отправкой. После продления старое напоминание не отправляется. Для
диагностики смотреть outbox status/age и auth-email delivery state, не печатать
payload с адресом или одноразовой ссылкой. Проверка реального SMTP в production
остаётся отдельной задачей; в локальном runtime SMTP выключен.

Telegram для входа и Telegram для алертов — разные назначения. Не переносить
webhook соседнего бота. Настроить отдельные env по `.env.example`. Балансы
provider account проверяются в фоне; низкий остаток ниже 500 ₽ создаёт
повторяемое уведомление до подтверждённой доставки. Новый alert появляется
после восстановления баланса и повторного падения, а не каждую минуту.

## Восстановление свежей копии и нагрузочная приёмка

`infrastructure/vps/test-restore.sh` проверяет SHA256 локальных dump, создаёт
отдельный PostgreSQL на случайном loopback-порту, восстанавливает четыре базы,
применяет текущие миграции и сравнивает количество строк существовавших таблиц.
Исходные backup сохраняются; изолированная восстановленная копия удаляется.

```bash
SEO_PLATFORM_RESTORE_CONFIRM=RESTORE_TO_ISOLATED_CLUSTER \
SEO_PLATFORM_RESTORE_BACKUP_DIR=/home/dev/.local/share/seo-platform-runtime/backups/КАТАЛОГ \
  infrastructure/vps/test-restore.sh
```

Для повторных browser/load проверок не отключать rate limits регистрации.
`prepare-session-fixtures.mjs` создаёт только 16 специальных тестовых аккаунтов
и часовые сессии, без паролей и staff-ролей. Задать `SEO_PLATFORM_E2E_CONFIRM`,
`SEO_PLATFORM_SESSION_FIXTURES` с новым файлом внутри managed runtime/tmp/e2e.
Обычная регистрация отдельно проверяется runtime suite; загрузочные тесты
используют подготовленные сессии и настоящие API/tenant guards.
`multi-tenant-load.test.mjs` выполняет 180 чтений от 12 отдельных пользователей;
`operation-confirmation.test.mjs` использует контролируемые ответы цены/создания
для проверки отмены, обновления оценки и восстановления потерянного ответа.

Не удалять и не менять исполняемый shell runner во время его работы: shell
читает файл последовательно. Для повторов сначала дождаться завершения
предыдущего запуска. Сохранять результаты отдельно от секретных session fixtures.

В production переносятся код и миграции, а существующие volume и данные Dokploy
сохраняются. Не подменять production БД локальными базами с тестовыми аккаунтами.
Тестовые сессии финального browser/load прогона отозваны; для нового прогона
подготовить новый fixture-файл или переиздать сессии только этих же тестовых
пользователей через `SEO_PLATFORM_REISSUE_SESSION_FIXTURES`.
