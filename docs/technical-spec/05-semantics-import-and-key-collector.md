# Семантическое ядро, импорт и совместимость с Key Collector

## 1. Назначение

Модуль является основным рабочим инструментом SEO-специалиста и должен поддерживать миллионы запросов, массовые операции, историю, совместную работу и обогащение внешними данными.

### 3.3. Загрузка таблицы и поиск

- Первичное чтение опубликованного ядра выполняется через
  `GET /projects/{projectId}/keywords`; frontend не обращается к `seo-data`
  напрямую.
- Обязательна стабильная keyset/cursor pagination по `created_at DESC, id DESC`;
  offset pagination для больших ядер не используется.
- Размер страницы по умолчанию — 100, максимум — 1 000 строк. Пользователь
  выбирает размер блока infinite scroll из 100, 200, 500 или 1 000 строк;
  выбор сохраняется отдельно для проекта в локальных layout-настройках.
- Для каждого из этих размеров SEO Data сначала читает только упорядоченные
  keyword ID и один lookahead-ID, затем гидратирует ровно видимую страницу
  последовательными порциями не более 250 keywords. Lookahead не загружает
  группы, теги, custom values и метрики. Это удерживает Prisma/PostgreSQL
  parameter count и пиковую память в одинаковых границах для 100, 200, 500 и
  1 000 строк.
- Cursor связан с нормализованным поисковым запросом и не принимается при
  изменении фильтра.
- Подстрочный поиск выполняется по нормализованному тексту и использует
  trigram-индекс.
- Пустое поле поиска всегда объясняет текущую область: название обычной группы,
  «Без группы», «Корзина», «Весь проект» либо количество папок в открытом
  union-view. Переключение области обновляет placeholder без перезагрузки.
- Фоновая перезагрузка таблицы, включая realtime-изменение количества запросов,
  обновление метрик и повторный запрос после ошибки, сохраняет checkbox-выбор и
  визуальное выделение по стабильным ID запросов. Оба состояния очищаются при
  фактической смене проекта, папки, фильтра или поисковой области, но не при
  сортировке, пагинации или обновлении данных в той же области.
- Удаление checkbox-выбора или визуально выделенных строк вычитает из обоих
  независимых наборов только фактически удалённые keyword ID. Остальные
  checkbox-выбранные и выделенные строки сохраняются; при частичном успехе
  конфликтные строки также остаются в своих наборах для повторного действия.
- Фильтр по тегу принимает значение только из project-scoped searchable-списка
  активных тегов. Сопоставление идёт как регистронезависимая
  подстрока по `normalizedName`; пустой ввод не создаёт условие. Сортировка по
  тегам выполняется сервером до cursor pagination по первому нормализованному
  активному тегу, а строки без тегов в обоих направлениях остаются внизу.
- Первая страница может возвращать `totalApprox`; последующие страницы не
  должны повторять дорогой `count`.
- Header checkbox выбирает для массовых операций весь текущий серверный filter
  scope, а не только уже загруженный блок. Ctrl/Cmd+A после фокуса/выделения
  строки загружает тот же scope, но только визуально выделяет строки и не
  меняет checkbox-выбор. Оба явных действия последовательно исчерпывают keyset
  cursor, отменяют процесс при смене фильтра и не увеличивают стоимость
  обычного открытия таблицы. Ctrl/Cmd+клик добавляет и убирает отдельные
  визуально выделенные строки; контекстное меню раздельно копирует checkbox-
  выбор и визуальное выделение в текущем порядке таблицы.
- В дереве групп Ctrl/Cmd+A выбирает все обычные группы, включая потомков
  свёрнутых узлов. Shift+click использует только видимую плоскую проекцию:
  потомки свёрнутого узла в диапазон не входят, раскрытые потомки входят.
  Открытая группа имеет спокойный brand-soft фон и тонкую левую метку;
  дополнительные Ctrl/Cmd/Shift-выбранные группы получают более насыщенный
  фон, контрастную рамку и широкую левую метку, чтобы два состояния не
  смешивались визуально.
- Иконка слева от обычного поиска открывает body-only поиск по списку до 500
  уникальных строк. Поддерживаются точное совпадение, вхождение и наличие всех
  слов. Режим работает вместе с текущими фильтрами/сортировкой, не помещает
  список в URL и позволяет показать, выбрать все либо сразу передать найденные
  запросы в стандартный перенос по дереву папок.
- Начальный read model строки включает оригинальный и нормализованный текст,
  язык, tracking-флаг, основную группу, target URL, первые 10 тегов, источник,
  даты и версию. Расширенные метрики добавляются отдельными projections.
- UI обязан различать initial loading, empty core, empty search result,
  recoverable error, loading next page и normal state. На узких экранах
  таблица прокручивается внутри контейнера и не расширяет документ.
- Заголовок grid и настроенный порядок колонок остаются видимыми при пустом
  проекте, пустой выбранной группе и пустом результате поиска/фильтров;
  empty-state показывается внутри тела уже смонтированной таблицы.
- Пустая выбранная группа не считается пустым результатом фильтра: UI сообщает,
  что в группе ещё нет запросов, и предлагает открыть ручное добавление сразу с
  этой группой. Корневая группа «Все запросы» с нулевым счётчиком показывает
  аналогичное состояние проекта и ручное добавление без выбранной группы. Для
  системной корзины действие добавления не показывается.
- Применение фильтров и серверной сортировки обновляет строки внутри уже
  смонтированной таблицы, не перезагружает страницу и сохраняет допустимую
  позицию внутреннего scroll-контейнера. Предыдущие строки остаются видимыми до
  получения нового ответа; loading-state не должен изменять геометрию экрана.
- Общий счётчик запросов в шапке и у корня «Все запросы» сохраняет последнее
  подтверждённое сервером значение во время realtime-refresh. Он меняется
  только после нового точного `totalApprox`; размер первой страницы нельзя
  использовать как общий итог, пока `hasNext=true`.
- Сброс поиска и фильтров очищает только условия текущего представления: явно
  открытая папка или union выбранных папок не меняются и не переводятся на
  корневой уровень.
- Позиция поисковика показывается одной колонкой с логотипом, текущим значением
  и компактным предыдущим значением. Рост и падение различаются цветом и
  текстовой подписью; отдельная колонка с символом delta не используется.
  Предыдущее найденное значение определяется по keyword ID и поисковику через
  все технические контексты съёма: смена региона, устройства или профиля не
  сбрасывает дельту в состояние «Новая».
- При сортировке по позиции сервер до cursor pagination формирует три уровня:
  текущие найденные значения; текущий `not-found` с известной предыдущей
  позицией; запросы без единого найденного значения. Эти уровни сохраняют такой
  порядок для ASC и DESC, а направление меняет только числовой порядок внутри
  первых двух уровней. Если свежий съём не нашёл позицию, но предыдущее
  найденное значение известно, ячейка показывает `×` и `было N`.
- Сортировка по ИИ-позициям Яндекса и Google следует тому же трёхуровневому
  правилу для запросов с ИИ-ответом: текущие найденные позиции; потерянные
  позиции с последним найденным значением; запросы без найденной ИИ-позиции.
  Запросы без самого ИИ-ответа в последнем позиционном снимке либо без замеров
  всегда находятся в самом низу, независимо от исторической позиции.
  Правило действует до cursor pagination; ASC/DESC изменяет числовой порядок
  внутри первых двух уровней, не смешивая уровни между собой.
- Проекции Wordstat обозначаются как «База», `""` и `"!"`; заголовки содержат
  доступный маркер Яндекса и не повторяют слово «частотность» в каждой колонке.

### 3.3.1. Панель команд сбора

Основные сборы сгруппированы в три выпадающие кнопки с иконками, чтобы toolbar
не разрастался при добавлении новых provider workflow:

- `Wordstat`: «Собрать частотность» и «Парсинг»;
- `Сбор позиций`: «Собрать позиции» и «Собрать ИИ-ответы»;
- `Сбор конкурентов`: «Собрать конкурентов» и «Собрать ИИ-выдачу».

Каждая кнопка работает как toggle: первый клик открывает своё меню, повторный
клик по той же кнопке закрывает его, а клик по другой кнопке сразу заменяет
открытый список.

Обычная и ИИ-выдача конкурентов используют те же канонические scope picker,
проверку permission, idempotency, операции и настройки поисковика/региона, что
соответствующие позиционные workflow. Но это отдельный immutable purpose:
конкурентный запуск сохраняет собранные SERP/source rows независимо от того,
разрешил ли пользователь обновлять позицию сайта проекта. Галочка сохранения
позиции показывается только в двух конкурентных modal; в обычных «Собрать
позиции» и «Собрать ИИ-ответы» её нет.

### 3.4. Универсальное редактирование

- Действие «Изменить» в карточке запроса и действие «Теги» в контекстном меню
  открывают один редактор; во втором случае фокус сразу устанавливается на
  поле тегов.
- Для одного запроса редактор показывает текст, язык, приоритет, избранное,
  интент, группу, кластер, Целевой URL и теги и сохраняет строку через
  optimistic version check. Избранное и отслеживание выбираются доступным
  сегментированным переключателем, язык — searchable select, а Целевой URL
  всегда доступен как прямой input без промежуточного режима. Активное
  избранное в строке таблицы обозначается отдельной жёлтой иконкой звезды из
  общего icon pack.
- Массовая команда передаёт по каждой выбранной строке только exact
  `{id, version}` и отдельный patch изменяемых полей. Остальная проекция строки
  интерфейса не должна попадать в HTTP payload; это одинаково действует для
  массового редактирования и preview/apply очистки.
- В панели деталей блок и системная колонка называются `Целевой URL`. Если URL
  не назначен, справа показывается кнопка `+`, которая открывает компактный
  versioned редактор; после назначения на том же месте доступны штатные
  действия ссылки и копирования.
- Для нескольких запросов та же форма работает как массовая: значение
  «Не менять» не отправляет поле, а команда применяет только явно выбранные
  изменения к зафиксированному selection scope. Булевы поля используют три
  явных состояния, а пустой URL-input сохраняет прежнее значение; очистка URL
  выбирается отдельным компактным действием. Массовое редактирование,
  перенос в папку и preview/apply очистки не обрезают выбор старым синхронным
  пределом: Web делит его на последовательные versioned команды до
  `semanticKeywordBulkCommandMaxItems=200` строк и агрегирует полный результат;
  поэтому 457 и более выбранных запросов сохраняют весь scope.
- Успешный перенос не запускает повторное чтение первой страницы. Web сливает
  возвращённые `updatedItems` с уже загруженными строками, сохраняет метрики и
  cursor paging, удаляет из DOM только строки, покинувшие текущий folder scope,
  уменьшает его `totalApprox` и отдельно обновляет счетчики дерева групп.
- Диалог переноса использует searchable иерархическое дерево групп с явным
  раскрытием уровней, цветами и полным путём выбранной цели. Системная корзина
  не может быть целью обычного переноса; «Без группы» доступна отдельно.
  Перенос строки из «Корзины» одновременно восстанавливает её в целевой папке
  через тот же bulk workflow, без отдельного шага.
- Ручное добавление и одиночное редактирование запроса используют то же
  portaled searchable дерево вместо плоского списка путей. Системные группы не
  дублируются среди целей, «Без группы» показывается ровно один раз, а
  компактные строки и поле поиска не изменяют геометрию основной modal.
  Количество строк ручного добавления не имеет продуктового верхнего предела:
  Web проверяет и сохраняет их последовательными порциями по 100. После preview
  modal закрывается, таблица остаётся доступной, command bar показывает spinner,
  а toast — `added/processed/total`. Транспортный сбой сохраняет неподтверждённый
  хвост для явного повтора; каждая отдельная HTTP-команда остаётся bounded.
- На viewport до `920px` дерево групп доступно из шапки как отдельная
  выдвижная панель и не исчезает из пользовательского сценария. Кнопка закрытия
  находится внутри её шапки, а глубокие уровни обрезают название без
  горизонтальной прокрутки панели. На телефонах в шапке семантики остаётся
  полноширинный selector текущего проекта. Выпадающие меню Wordstat, позиций и
  конкурентов привязаны к нажатой кнопке, открываются непосредственно под ней и
  ограничиваются viewport. Контекстное меню группы и portaled picker папки
  открываются поверх контента нижним листом над фиксированной навигацией с touch
  targets не меньше `40–44px`; содержимое modal прокручивается отдельно от
  постоянно доступного footer с действиями.
- На телефонах toolbar таблицы занимает две стабильные строки: поиск — первую,
  фильтры и настройка вида — вторую. Таблица и command bar с видимыми текстовыми
  подписями прокручиваются только внутри собственных областей, а status bar
  заканчивается над фиксированной нижней навигацией и не перекрывается ею.

## 5. Нормализация

Нормализатор является версионируемым и конфигурируемым.

Доступные операции:

- trim;
- Unicode normalization;
- схлопывание пробелов;
- приведение регистра;
- нормализация кавычек;
- удаление/сохранение операторов;
- замена `ё/е` по настройке;
- нормализация дефисов;
- удаление служебных символов;
- нормализация URL;
- выделение языка;
- лемматизация по поддерживаемому языку.

В Keyword сохраняются оригинальное и нормализованное значения. Изменение правил нормализации не должно молча переписывать существующие данные; оно выполняется отдельной версионируемой операцией с preview.

## 6. Дедупликация

Режимы:

- точное совпадение оригинала;
- совпадение normalized;
- без учёта операторов;
- без учёта порядка слов;
- по леммам;
- пользовательская формула.

Действия при дубле:

- пропустить;
- объединить значения по правилам;
- заменить существующую строку;
- создать вариант;
- отправить в отдельную группу конфликтов.

При объединении пользователь видит, какие поля будут сохранены, перезаписаны или конфликтуют.

Ручное объединение canonical keywords выполняется отдельной CAS-командой с
явным keeper. `keyword_merges` хранит source → target; source скрывается из
рабочей таблицы, а его immutable frequency/rank/SERP/AI history читается как
история keeper. Папки, теги, заметки, custom values и активные tracking
assignments переносятся транзакционно. Поиск в настройках предлагает bounded
пары для названий с ошибками кодировки, но ни одна пара не применяется без
checkbox и выбранного keeper.

### 6.1. Ручное массовое добавление

- Один пользовательский запуск принимает до 2 000 строк; Web отправляет их
  последовательными chunk по 100 строк, сохраняя исходный индекс каждой строки.
  Повторы внутри вставленного списка схлопываются до предварительной проверки и
  не создают несколько решений для одной canonical identity.
- До первой мутации Web вызывает `POST /keywords/bulk-preview`. Core SEO
  сопоставляет нормализованные ключи внутри проверенного workspace/project и
  возвращает для каждой строки состояние, ID/version совпадения, все доступные
  текущие group membership (bounded до 50 с признаком truncation) и признак
  присутствия в целевой группе. Текст запроса не отражается в ответе: Web
  связывает результат с исходной строкой по индексу.
- При найденных совпадениях Web показывает review-таблицу «запрос → текущие
  группы → действие». Перед preview пользователь выбирает один из трёх
  взаимоисключающих режимов в segmented control: `Не добавлять` пропускает
  совпадения во всём проекте; `Сохранить группы` добавляет группу из формы с сохранением
  текущих membership; `В эту группу` переносит совпадения в уже открытую
  обычную группу слева, а при открытом корне — в обычную группу из уже
  существующего поля «Группа», без дополнительного selector, и снимает
  остальные memberships. Сам режим всегда доступен для выбора; если цель ещё
  не задана, UI просит выбрать обычную группу в основном поле. Режимы задают
  начальный выбор `ADD_TO_GROUP` или
  `MOVE_TO_GROUP`, после
  чего решение можно изменить для каждой активной строки и строки из
  «Корзины». Выбранные совпадения добавляются в целевую папку и остаются в
  прежних обычных папках только в режиме `Сохранить группы`; `В эту группу`
  оставляет ровно одну целевую membership без создания копии keyword identity, а выбранные
  строки из «Корзины» восстанавливаются в целевую группу. Остальные получают
  `SKIP_EXISTING`; отсутствие выбора не считается ошибкой. Строка, уже
  состоящая в целевой группе, недоступна для повторного выбора.
- Команда первичного добавления явно передаёт `duplicatePolicy`:
  `SKIP_EXISTING`, `ADD_TO_GROUP` или `MOVE_TO_GROUP`. Активное совпадение
  никогда не создаёт вторую keyword identity. `ADD_TO_GROUP` атомарно добавляет
  явно выбранную обычную папку, сохраняет прежние обычные membership и удаляет
  только системную membership «Без группы». Команда увеличивает версию строки,
  записывает полный список папок в историю и возвращает совместимый outcome
  `LINKED_EXISTING`. Без выбранной папки действие недоступно.
- `MOVE_TO_GROUP` под теми же блокировками удаляет все memberships активного
  совпадения и создаёт одну membership целевой обычной группы. Если строка уже
  находится только в ней, команда остаётся идемпотентным skip.
- Совпадение в «Корзине» не восстанавливается молча: review показывает для него
  отдельный checkbox. Выбранная строка отправляется с явным действием
  `RESTORE_TRASHED` и восстанавливается в целевую папку (либо в «Без группы»,
  если папка не выбрана); невыбранная строка остаётся в «Корзине». Для импорта
  сохраняется двухэтапный порядок: завершённый import receipt возвращает
  bounded список совпадений из «Корзины», после чего пользователь выбирает
  восстанавливаемые запросы в следующем modal. Отмена не изменяет «Корзину».
- `SKIP_EXISTING` возвращает `SKIPPED_EXISTING`, а `REJECT_EXISTING` —
  row-level `REJECTED_EXISTING`; остальные строки одного запуска продолжают
  обрабатываться. Bulk policy остаётся fallback, а опциональный row-level
  `duplicatePolicy` применяет подтверждённое решение к конкретной строке.
- Начальные состояния обоих checkbox хранятся как отдельная per-project
  пользовательская Web-настройка; настройка одного проекта не изменяет
  поведение другого. Старое сохранённое значение безопасно мигрируется в пару
  взаимно независимых опций.
- Устаревшая `DELETED`-запись без членства в «Корзине» восстанавливается тем же
  ID через tenant-scoped CAS, получает новое членство/теги и не резервирует
  дополнительную stored capacity. Новый нормализованный ключ создаётся только
  после проверки workspace/project capacity.
- Ответ содержит `selected/created/restored/skipped/rejected/failed` и ровно
  один индексированный outcome на входную строку. Тексты запросов и секреты в
  ответ, audit и внутренние логи не копируются.
- Только bulk-create routes принимают body до 8 MiB; валидатор ограничивает
  сериализованный payload шестью MiB. Остальные API routes сохраняют штатный
  меньший лимит.

## 7. Группы

- Иерархия без фиксированной глубины, но UI оптимизирован до 10 уровней.
- Группа имеет название, цвет, родителя, sort order, описание и владельца.
- Активная строка группы использует усиленный brand-фон, рамку, левый акцент и
  полужирное название, чтобы выбор не терялся среди hover/selected состояний.
- Каждый общий иерархический picker при открытии раскрывает всю цепочку
  родителей текущей выбранной группы и центрирует её строку в scroll-области.
  Это поведение одинаково для фильтров, переноса, импорта и настроек.
- Запрос может находиться в нескольких группах; таблица показывает выбранную
  группу в текущем контексте, а импорт не теряет остальные членства.
- Пользователь может выбрать от двух обычных групп и открыть union их запросов
  без создания новой группы. Продуктового верхнего лимита на число папок в
  union нет; практические пределы задаются только общими bounded HTTP/DB
  контрактами. Query, cursor и server-side
  sorting связываются со всем отсортированным набором ID; в union-view колонка
  группы включается принудительно, даже если скрыта сохранённым представлением,
  и сохраняет пользовательскую регулировку ширины. Под запросом в обычной
  плотности показываются компактные теги, а служебная текстовая подпись языка и
  отслеживания не выводится. Если `isTracked = false`, непосредственно перед
  текстом запроса в обеих плотностях показывается компактная иконка
  перечёркнутого глаза. Текущая
  открытая обычная группа считается первым элементом выбора: Ctrl/Cmd+клик по
  второй группе сразу формирует выбор из двух групп. Контекстный клик по группе,
  которая не входит в текущую мультивыборку, заменяет выбор этой группой и
  открывает её; контекстный клик внутри уже собранной мультивыборки сохраняет
  batch scope.
- При выборе более 20 групп Web и межсервисные клиенты используют body-only
  `POST /keywords/list`; UUID не попадают в длинный query string. Public,
  internal и export-контракты принимают до 2000 уникальных project-scoped
  групп, а realtime presence публикует только bounded проекцию до 50 ID и не
  является источником фильтра. Это предотвращает ошибку URI при большой
  мультигруппе и сохраняет тот же cursor/filter hash.
- Мастера операций не материализуют scope через полную табличную проекцию.
  `POST /projects/{projectId}/keywords/operation-scope` возвращает только
  `id`, `version`, `isTracked`, точный `totalApprox` на первой странице и до
  10 000 строк за cursor-страницу. Проектный scope и union до 20 000 папок
  используют один tenant-scoped запрос; метрики, теги и custom values в этот
  transport не входят. Клиент проверяет лимит операции по `totalApprox` до
  загрузки остальных страниц.
- Контекстное меню обычной группы сразу после экспорта показывает компактную
  палитру всех шестнадцати цветов на всю доступную ширину в две строки по
  восемь образцов. Выбор цвета применяется ко всей
  текущей мультивыборке групп с optimistic version check для каждой строки; системные
  группы не перекрашиваются. Быстрая палитра и диалоги создания/изменения
  используют один общий каталог: красный `#ff0000`, оранжевый, жёлтый, лаймовый,
  зелёный, изумрудный,
  бирюзовый, синий, индиго, фиолетовый, розовый, нейтральный серый,
  коричневый, бордовый, петрольный и графитовый; крупные
  образцы расположены в две строки под ручным выбором и HEX-полем.
- Рядом с заголовком `Группы` находится кнопка проектного примечания по цветам.
  Она открывает общую для всех участников легенду из тех же 16 фиксированных
  цветов; у каждого цвета можно хранить одно нормализованное пояснение длиной до
  240 символов. Читать легенду может любой участник с `semantic.view`, а менять
  — только пользователь с effective permission
  `semantic.manage_group_color_legend` (системные роли SEO Lead, Admin и Owner
  при project access `MANAGER`). Изменение выполняется через `If-Match`, повышает
  проектную версию и автоматически отмечается просмотренным автором. Для
  остальных пользователей Core SEO хранит персональный `seenVersion`; пока он
  меньше текущей версии, на кнопке виден бейдж. Открытие modal отправляет
  идемпотентную отметку просмотра, а data-free realtime hint заставляет другие
  вкладки перечитать легенду через HTTP API. Источником истины остаются таблицы
  `semantic_group_color_legends` и `semantic_group_color_legend_reads`, а не
  browser storage или WebSocket. В полях пояснений работают обычные текстовые
  сочетания, включая Ctrl/Cmd+A: глобальное выделение дерева не перехватывает
  событие из input/textarea/contenteditable. Если у цвета текущей группы есть
  пояснение, контекстное меню показывает его read-only строкой с иконкой info
  непосредственно ниже действия удаления.
- Создание из контекстного меню явно разделено на действия «Создать внутри» и
  «Создать рядом»; верхняя кнопка `+` создаёт корневую группу. Диалог показывает
  итоговое расположение через searchable дерево и позволяет сменить его до
  сохранения. Названия вводятся или вставляются обычным текстом — по одному на
  строке; пустые строки игнорируются, а порядок непустых строк сохраняется.
  Одна команда принимает от 1 до 200 уникальных названий и атомарно создаёт их
  подряд на выбранном уровне: при конфликте или превышении лимита не создаётся
  ни одна папка. «Создать рядом» вставляет весь список
  непосредственно ниже группы, на которой было открыто меню; при выборе другого
  уровня список добавляется в конец выбранного уровня.
- Обычную группу можно дублировать с optimistic version check. По умолчанию
  создаётся соседняя папка с безопасным свободным названием и копируется всё
  дерево подгрупп; копирование прямых членств запросов по умолчанию выключено.
  Пользователь до запуска может изменить имя/родителя и независимо включить
  копирование запросов либо отключить вложенные папки. Копируются только
  memberships существующих canonical keyword ID — новые запросы и текстовые
  дубли не создаются; системные группы дублировать нельзя.
- Перетаскивание обычной группы использует расширенные верхнюю и нижнюю зоны
  строки для ручного порядка, а её компактный центр — только для явного
  вложения. Между соседями одного уровня показывается одна позиция. На границе
  последнего раскрытого потомка и следующей внешней группы сохраняются две
  намеренно разные цели: нижняя кромка потомка оставляет группу на вложенном
  уровне, верхняя кромка внешней строки вставляет её на внешнем; отступ линии и
  плавающая подпись над drag-preview всегда показывают выбранный уровень до
  отпускания мыши и не перекрываются переносимой папкой или запросом.
- Двойной клик по названию обычной группы включает inline-переименование без
  изменения размеров и колонок строки. `Enter` и потеря фокуса сохраняют
  нормализованное название через optimistic version check, `Escape` отменяет;
  выделение, удаление и редактирование текста работают как в обычном поле.
- Дополнительная классификация выполняется тегами.
- Перемещение большой группы — асинхронная операция.
- В каждом проекте существуют защищённые системные группы «Без группы» и
  «Корзина»: их нельзя переименовать, вложить в другую папку или удалить.
- Активный запрос без обычной группы автоматически состоит в «Без группы».
- Обычное удаление запроса переносит его в «Корзину»; необратимое удаление
  разрешено только из неё. Оно уничтожает пользовательский текст, членства,
  теги и custom values и освобождает уникальную нормализованную identity.
  Непрозрачный технический tombstone сохраняется только для неизменяемой
  исторической provenance позиций и не отображается как запрос проекта.
- При удалении дерева групп checkbox «Переместить запросы в корзину» выключен
  по умолчанию. В этом режиме членства удаляемого дерева снимаются, а запросы
  без другого членства переходят в «Без группы». Включённый checkbox переносит
  все запросы дерева в «Корзину».
- При удалении одной обычной группы с непосредственными подгруппами доступен
  отдельный выключенный по умолчанию checkbox сохранения подгрупп. При его
  включении удаляется только выбранная группа, а непосредственные дочерние
  группы атомарно занимают её место на уровне родителя либо в корне; их порядок,
  вложенность, запросы и пересчитанные полные пути сохраняются. Конфликт полного
  пути отменяет всю команду без частичного переноса.
- Количество запросов пересчитывается асинхронно и допускает временный `calculating`.

## 8. Кластеры

- Кластер может быть ручным или автоматически созданным.
- Содержит название, тип, confidence, метод, параметры, SERP snapshot IDs и target page.
- В группе может быть несколько кластеров.
- Запрос может находиться в одном активном кластере; история перемещений сохраняется.
- Поддерживаются merge, split, rename, lock и exclude from reclustering.
- Locked cluster не изменяется автоматической кластеризацией.
- Массовое назначение посадочной не имеет продуктового лимита в 200 кластеров:
  Web сохраняет весь выбор, последовательно выполняет bounded versioned команды
  по `semanticClusterPageBulkMaxItems=200` и агрегирует preview/result. Лимиты
  атомарных merge/split не маскируются пакетированием и остаются отдельными.

### 8.1. Методы кластеризации

- soft;
- middle;
- hard;
- порог общего числа URL;
- процент пересечения ТОП;
- выбранная глубина ТОП;
- поисковая система;
- регион;
- устройство;
- дата/свежесть SERP.

Результат кластеризации сначала создаётся как proposal:

- preview;
- статистика изменений;
- новые/удалённые кластеры;
- конфликты locked entities;
- стоимость;
- apply;
- reject.

### 8.2. Реализованный Arsenkin clustering workflow

Команда `Кластеризовать` принимает явный список versioned keyword ID либо
разрешает его из выбранных папок/всего проекта до 300 000 запросов — это единый
Arsenkin limit в UI, public/internal validation, Jobs broker и proposal
storage. Пользователь выбирает Arsenkin credential, Яндекс/Google, регион,
soft/hard, порог
пересечения `2..10`, глубину `10|20|30`, исключение главных страниц,
стоп-домены и виды частотности. Public enum `BASE|QUOTED|OVERALL|EXACT`
передаётся в документированный Arsenkin `ws` array как
`base|quoted|overal|exact`; по умолчанию все частотности выключены и `ws`
пуст. Жёсткая группировка расположена слева и выбрана по умолчанию. Первый
запуск для Яндекса и Google использует Москву (`213` и `1011969`); после
успешного запуска Web восстанавливает последний регион отдельно для проекта и
поисковика.
Существующие кластеры по умолчанию не перезаписываются: checkbox запуска задаёт
автоматический default, но окончательное решение принимается отдельно для
каждого provider-кластера в review.

Execution создаёт отдельный `CLUSTERING_RUN` и выполняет документированный
Arsenkin lifecycle `set → check → get`. Один запуск является одной provider
task над immutable scope. Он делит пять durable Arsenkin slots с rank,
Wordstat и AI answer; submit имеет persisted marker, lease/version fencing и
при неоднозначном transport outcome переходит в `ACTION_REQUIRED`, а не
повторяет платную отправку. WebSocket не участвует в источнике истины.
Connector `arsenkin-clustering@1.1.0` принимает фактический nested result
`result.clustering.clustered|single`, разворачивает object-keyed `words` в
строки и сохраняет cluster-level `topurl/wssumm` отдельно от per-word полей.
Нормализуется до 100 top URL на кластер с необязательным числом пересечений;
это bounded evidence хранится отдельно от raw ответа провайдера.

Нормализованный provider result не изменяет семантику напрямую. Core SEO
идемпотентно сохраняет `ClusteringProposal`, его кластеры и построчные items с
исходными keyword version. Результат доступен в drawer «Операции», общем
журнале и private/noindex modal/page. Preview показывает proposed/current
cluster, частотность, geo и состояния `READY|UNCHANGED|LOCKED|EXCLUDED|
CONFLICTED|UNAVAILABLE`. Назначенный ранее SEO-кластер не является конфликтом:
строка остаётся `READY`, а UI показывает его как текущее безопасное назначение.
`CONFLICTED` с причиной `KEYWORD_CHANGED` означает только реальное изменение
версии после запуска; SEO-кластер и папка семантики не смешиваются.

Сводка содержит все bounded descriptors provider-кластеров, но строки не
материализуются целиком. Общая result-страница остаётся cursor-paginated, а
каждая развёрнутая видимая карточка отдельно загружает до 200 своих строк через
tenant-scoped `result/sections/:sectionId`. Cursor использует исходный
immutable `sequence` и допускает разрывы между строками одного кластера.
Карточка всегда показывает `загружено / всего`; следующая страница запрашивается
явно, поэтому preview остаётся пригодным и при лимите 300 000 запросов.

Перед apply пользователь может переименовать proposed clusters. Для каждого
provider-кластера независимо выбираются два назначения: создать новый
SEO-кластер, использовать конкретный существующий либо сохранить текущие
назначения; и отдельно создать папку под выбранным прямо в карточке parent,
перенести в существующую либо не переносить. При выключенной перекластеризации
и наличии текущих SEO-кластеров безопасный default — сохранить их; для новой
папки default — корень проекта. Locked и excluded SEO-кластеры нельзя выбрать
как цель. Выбранные parent новой папки и target существующей папки сохраняются
в локальном черновике независимо: переключение селекта между «создать»,
«существующая» и «не переносить» не сбрасывает их. В apply command включается
только destination активного режима, чтобы trusted exact parser не принимал
скрытые взаимоисключающие поля.
Каждая option обоих селектов содержит унифицированную иконку действия:
`folderPlus` для создания, `move` для переноса в существующее и нейтральный
`minus` с прямой подписью «Ничего не делать» для сохранения текущего состояния.
Та же option целиком показывается в закрытом trigger. Embedded result workspace
занимает всю ширину и высоту body модалки без внешних padding; отступы остаются
только внутри его собственных панелей и строк.
Выбранные строки можно направить в другие существующие папки независимо от
остального кластера; row override имеет приоритет. Некластеризованные запросы
по умолчанию остаются в текущих папках, опционально создаётся папка
«Некластеризовано». Назначение новой/существующей папки удаляет прежние обычные
membership запроса, а «Не переносить» сохраняет их. Apply выполняется одной SEO-транзакцией с advisory locks,
повторной проверкой versions/locked/excluded entities, тарифного лимита папок
и создаёт semantic versions пакетами не более 500 изменений. Proposal после
этого становится `APPLIED`; reject переводит его в `REJECTED` без изменения
семантики. Повторный apply/reject запрещён optimistic version boundary.

## 9. Теги

- Несколько тегов на запрос.
- Теги имеют цвет, описание и scope workspace/project.
- Выбор и создание тегов выполняются через чипы и searchable select с
  project-scoped подсказками. Запятая является частью имени, не разделителем.
- Массовый UI разделяет «Добавить теги» и «Снять теги»: добавляет указанные
  теги ко всем выбранным строкам и снимает только явно указанные. Остальные
  индивидуальные теги каждой строки сохраняются. Полной замены набора нет.
  Снятие предлагает теги выбранных запросов; крестик на чипе отменяет это
  действие до применения формы. Блок тегов занимает отдельную строку и не
  растягивает соседние поля.
- Одиночный редактор снимает только явно удалённые чипы и добавляет новые
  через delta-команду. Исторический API `tagNames` сохраняет явную replacement
  семантику для совместимости и не смешивается с `addTagNames/removeTagNames`.
- Системные теги могут вычисляться автоматически, но пользовательские теги не удаляются автоматизацией.
- В панели фильтров у выбранного пользовательского тега показывается действие
  удаления. Перед командой modal показывает точное число связанных запросов;
  подтверждение атомарно снимает tag membership со всех запросов проекта,
  увеличивает версии затронутых keywords и переводит сам тег в `DELETED`.
  Аналогичное действие для SEO-кластера атомарно очищает `clusterId` у всех
  связанных запросов перед переводом кластера в `DELETED`. Обе команды
  tenant-scoped, требуют `semantic.update`, CSRF и фиксируются в аудите.

## 14. Сохранённые виды

Текущий контракт `schemaVersion: 4` содержит:

- фильтры;
- sorting;
- упорядоченный набор видимых системных и пользовательских columns;
- полный порядок column catalog, включая временно выключенные колонки;
- включённые индикаторы внутри закреплённой колонки запроса: несколько URL и
  несовпадение найденного URL с целевым; сохранённый legacy-признак
  `AI_ANSWER` принимается для совместимости, но отдельную иконку у запроса не
  рисует;
- widths колонок;
- density;
- размер порции infinite scroll;
- ширину дерева групп;
- раскрытые группы;
- выбранную группу или union групп.

Версия 4 добавляет `rankSortDimensionKey` для сортировки по позиции или дате
динамической географической колонки. Поле обязательно только для
`RANK_POSITION_*` и `RANK_CHECKED_AT_*`, идентифицирует точное сочетание
поисковика, страны, региона, языка и устройства и входит в cursor/filter hash.
Такой же ключ фиксируется в export snapshot, поэтому экспорт не меняет порядок
строк относительно сохранённого вида. Jobs → SEO Data сериализует
`rankSortDimensionKey` вместе с `sort` во всех GET-чтениях таблицы,
конкурентов и истории; потеря ключа недопустима и не должна превращать
корректный export Job в `SEO_DATA_INVALID_COMMAND`.

Версия 2 включает отдельные системные колонки `yandexRelevantUrl` и
`googleRelevantUrl` для обычного позиционного съёма. Версия 3 добавляет
`yandexAiRelevantUrl` и `googleAiRelevantUrl`: это найденные URL домена проекта
из последних ИИ-ответов Яндекса и Google. Серверы принимают версии 1, 2, 3 и 4 для
rolling compatibility. При чтении версии 1 Web вставляет обычные и ИИ URL сразу
после соответствующих колонок позиции; при чтении версии 2 — только ИИ URL.
При переходе версий 3 → 4 состав и явная видимость колонок не меняются.

В серверный `columnWidths` входят только колонки, присутствующие в `columns`
этого представления. Локальные ширины временно скрытых колонок могут оставаться
в browser layout preferences, но перед созданием, обновлением или
автосохранением view они отфильтровываются; отключение колонки поэтому не
делает конфигурацию невалидной и не влияет на cursor текущей выборки.
При явном применении layout новый порядок, видимость, плотность и карта ширин
берутся из одного draft-снимка и сохраняются атомарно; поля старого набора
колонок не могут попасть в итоговый payload даже при массовом отключении.
В панели настройки выключенная колонка остаётся на своей позиции в общем
упорядоченном списке и меняет checkbox/иконку на неактивное состояние. Её
позиция хранится отдельно в `columnOrder`, поэтому повторное включение, новый
вход и применение private или project-shared view не перемещают строку вниз.
Старые представления без `columnOrder` восстанавливают каталог из порядка
видимых колонок и дополняют его доступными колонками.
Три индикатора запроса выводятся вложенными пунктами под закреплённой колонкой
`Запрос`. Для старого view без `queryIndicators` они все включены; явный пустой
массив отключает все три. Настройка входит в тот же атомарный draft и одинаково
сохраняется в private и project-shared views.

Служебный private-layout дополнительно может хранить `appliedViewId` — UUID
видимого представления, которое применил конкретный пользователь. Это
персональная серверная настройка: она не меняет общий view и восстанавливается
после нового входа или на другом устройстве.

Поддерживаемый scope:

- `PRIVATE`: любой участник проекта создаёт собственный вид, изменять и удалять
  его может только владелец;
- `PROJECT_SHARED`: виден всем участникам проекта, а создавать, обновлять и
  удалять его могут только роли `OWNER` и `ADMIN`.

Выбранный private view сохраняется автоматически после изменения фильтра,
сортировки, колонок, ширины, плотности или состояния дерева. PATCH использует
версию и `If-Match`; при конфликте `412` autosave останавливается и предлагает
заново открыть актуальное представление. Общий view применяется локально как
read-only конфигурация и изменяется только явным действием администратора
`Обновить`, поэтому просмотр общего вида участником не меняет его у коллег.
Служебное private-представление текущего layout скрыто из пользовательского
списка, но подчиняется тем же правилам владения и optimistic concurrency.
У каждого видимого представления есть отдельная кнопка применения. Применённое
представление отмечается в списке; если текущий layout отличается от его
сохранённой конфигурации, рядом выводится состояние «Изменения не сохранены».
Если явный `appliedViewId` отсутствует или ссылается на удалённый view,
интерфейс выбирает project-shared представление «Общее для проекта», а при его
отсутствии — первый доступный общий вид. Portaled select/popover внутри drawer
считается частью drawer и не закрывает его по outside-click.
Workspace templates и client-published views не входят в `schemaVersion: 4`.

## 15. Массовые операции

- перемещение;
- кластеризация;
- назначение URL;
- изменение тегов;
- изменение статуса/приоритета;
- включение отслеживания;
- сбор частотности;
- съём позиций;
- удаление;
- merge;
- очистка;
- применение пресета минус-слов;
- формула/преобразование колонок;
- экспорт.

Каждая массовая операция:

- фиксирует filter snapshot/selection;
- показывает scope;
- рассчитывает влияние;
- при необходимости оценивает стоимость;
- создаёт job;
- ведёт row-level result;
- может быть отменена до необратимого этапа;
- создаёт semantic version и undo package.

Одиночное и массовое изменение `isTracked` проходит через обычную versioned
keyword-команду. Выключенный запрос остаётся в папках, контекстах, истории и
таблице, но по умолчанию не материализуется в новый manifest съёма позиций.

Экспорт семантики не выполняется в синхронном HTTP-запросе: для выбранных
строк, текущего фильтра, дерева папки или всего ядра создаётся фоновый Job.
Поддерживаются CSV, TSV, JSON, NDJSON, Google CSV и Excel XLSX. Job показывает
прогресс, допускает кооперативную отмену и после завершения выдаёт
короткоживущую подписанную ссылку; закрытие диалога не останавливает экспорт.
Полный и отфильтрованный scope обрабатываются постранично и не имеют старого
синхронного ограничения в 2 000 строк.
В XLSX частотности (`BASE`, `EXACT`, `FIXED`) и позиции Яндекса/Google
записываются нативными числовыми ячейками; отсутствующее измерение остаётся
пустой ячейкой, а не текстовым маркером.

Отдельный XLSX scope `FOLDER_MAP` формирует книгу «Карта сайта по папкам».
Пользователь явно выбирает одну или несколько обычных папок; по умолчанию
учитываются только сами папки. Компактная кнопка «Вложенные» отдельно включает
все их поддеревья и отмечает каждую включённую строку дерева. Worker сверяет
выбранные UUID с актуальным
tenant-scoped деревом, исключает системные папки, дедуплицирует пересекающиеся
поддеревья и сохраняет относительную иерархию выбранного набора. Первый лист
`Карта` показывает только дерево папок без служебной колонки количества; пустые
папки остаются в структуре без лишнего листа. Для каждой непустой папки
создаётся отдельный лист с обязательной колонкой запроса и выбранными
пользователем дополнительными колонками. Запрос читается отдельно по каждому
group membership, поэтому при членстве в нескольких выбранных папках законно
присутствует на нескольких листах. Названия листов очищаются по правилам Excel,
ограничиваются 31 символом и получают устойчивый уникальный суффикс. С карты
есть внутренние ссылки на листы папок, а в первой строке каждого листа — ссылка
обратно на соответствующую строку карты. Новая очередь, таблица и deployable
для режима не создаются.

Отдельный режим XLSX «История позиций» принимает один или оба поисковика и
полуоткрытый UTC-диапазон дат. По умолчанию scope содержит только запросы с
`isTracked = true`; пользователь может явно включить неотслеживаемые запросы в
выгрузку. Он использует тот же фоновый `SEMANTIC_EXPORT`,
но выбирает BYOK-снимки каждого keyword ID независимо от tracking context и
выводит только фактически существующие даты. Яндекс и Google получают отдельные
листы; первые строки содержат формулы долей TOP-5, TOP-10 и TOP-30. Позиции
являются числовыми Excel-ячейками, отсутствие позиции обозначается прочерком.
Сравнение каждой строки выполняется с предыдущим фактическим замером этого же
keyword ID и поисковика: первое появление и улучшение — зелёные, ухудшение и
пропажа — красные, неизменная позиция — нейтральная. Если позиции не было ни в
текущем, ни в предыдущем замере, прочерк остаётся нейтральным. Даты, в которые
конкретный запрос не проверялся, не считаются `not-found` и не сбрасывают базу
сравнения.

В обычном выборе колонок `SEMANTIC_EXPORT` доступны четыре export-only поля:
URL конкурентов обычной выдачи, их SERP-данные, URL ИИ-конкурентов и их
SERP-данные. Для каждого keyword ID и поисковика выбирается последний доступный
snapshot, включая нормализованный `KEY_COLLECTOR`; из обычной выдачи
используются первые десять результатов, из
ИИ-ответов — сохранённые source URL. Собственный домен проекта исключается, а
одинаковые нормализованные URL объединяются внутри одного keyword и источника.
Каждый keyword сохраняет одну строку обычной таблицы экспорта. Несколько URL в
одной ячейке разделяются переводами строк; соседняя SERP-ячейка содержит блоки
`Title: {title}\nDescription: {description}`, также разделённые переводами строк.
CSV/TSV экранируют встроенные переводы строк, XLSX включает перенос текста
внутри ячеек.

Помимо export-only полей, обычный экспорт принимает четыре системные URL-колонки
таблицы: URL последнего позиционного съёма и URL последней ИИ-выдачи отдельно
для Яндекса и Google. ИИ URL берётся из `aiAnswers[].rankingUrl`; отсутствие
домена проекта в источниках экспортируется пустым значением, а не URL
конкурента.

После terminal `COMPLETED` Web показывает обычную ссылку «Скачать файл» на
tenant-scoped `GET /api/v1/projects/:projectId/exports/:exportId/file`. Core
повторно проверяет сессию, проект и `semantic.export`, журналирует авторизацию
скачивания, получает у Execution короткоживущую object-storage URL и потоково
передаёт артефакт через same-origin BFF с `attachment` `Content-Disposition`.
Браузер не переходит на S3 endpoint и не зависит от доступности отдельного
storage-порта из клиентской сети; скачивание начинается непосредственным кликом
пользователя и не зависит от browser user-activation, потерянной за время
фонового polling. Поток не материализуется целиком в памяти Core или Web.

## 16. Версионирование

Версия создаётся для:

- импорта;
- массового изменения;
- кластеризации;
- дедупликации;
- изменения URL;
- удаления;
- применения автоматического предложения.

Версия содержит:

- actor;
- source job;
- timestamp;
- summary;
- affected count;
- before/after diff;
- reversible flag;
- parent version.

Восстановление:

- сначала preview;
- не откатывает более новые несвязанные изменения без предупреждения;
- конфликтующие строки перечисляются;
- само восстановление создаёт новую версию.

## 17. Импорт: форматы

Поддерживаются:

- CSV;
- TSV;
- XLSX;
- XLS;
- ZIP с одним или несколькими поддерживаемыми файлами;
- вставка из clipboard;
- JSON через API;
- импорт из подключённого источника.

### 17.1. CSV/TSV

- UTF-8, UTF-8 BOM, Windows-1251 и определение encoding;
- delimiter auto-detect и ручной выбор;
- quote/escape;
- header/no header;
- переносы строк внутри quoted fields;
- preview первых строк;
- отчёт о повреждённых строках.

### 17.2. Excel

- выбор листов;
- пропуск скрытых листов по умолчанию;
- выбор строки заголовка;
- обработка merged cells по явному правилу;
- формулы импортируются как отображаемые значения с предупреждением;
- даты нормализуются с учётом locale;
- лимиты XLSX проверяются до обработки.

Для истории позиций поддерживается широкая таблица: первая колонка содержит
фразу, остальные измерения представлены датами. Один файл соответствует одной
выбранной поисковой системе. `-`, `–` и `—` означают выполненную проверку без
найденной позиции; пустая ячейка означает, что проверка в эту дату не
выполнялась. Целые значения и табличные числа вида `7.0` импортируются как
позиции `1..100`. Строки `ТОП-5/10/30` считаются сводными и пропускаются с
явным диагностическим кодом.

Также поддерживается построчный формат, где каждая строка содержит запрос,
дату, позицию и при необходимости URL найденной страницы из выдачи,
поисковик, город, код региона, устройство, страну и язык. URL из выдачи
сохраняется в `rankingUrl` конкретного снимка и не заменяет назначенный
`targetUrl` запроса. Явные значения строки имеют приоритет над defaults мастера;
широкий и построчный варианты публикуются через один append-only history path.

Файл, созданный экспортом SEOньориты, содержит отдельные поля языка keyword,
поисковика, города, кода региона, устройства, страны и языка выдачи. Контекст
строки имеет приоритет над defaults мастера; неизвестные явные значения
отклоняются, а не заменяются молча. Импорт создаёт append-only manual snapshots
с исходной датой и provenance `MANUAL_IMPORT`; новая дата не переписывает
старую, а current projection меняется только на более новый замер. Экспорт и
повторный импорт обязаны сохранять числа, `not-found`, пустые даты и
географические срезы без потери смысла.

CSV, TSV и XLSX используют единую модель: один табличный набор данных, а
вложенность хранится полным путём в одной колонке группы. Разделитель задаётся
mapping; поддерживается до 64 уровней, при публикации создаются все префиксы
пути от корня до конечной папки.

### 17.3. Key Collector

Поддерживается импорт CSV/TSV/XLSX, экспортированных из Key Collector, и
нативного проекта `.kc4`.

Wizard должен распознавать и предлагать mapping:

- фраза;
- группа и иерархия групп;
- базовая/точная/фиксированная частотность;
- регионы;
- позиции;
- релевантная страница;
- поисковая система;
- дата проверки;
- теги/цветовые маркеры;
- KEI и пользовательские показатели;
- служебные колонки;
- пользовательские колонки.

Неизвестные колонки:

- можно пропустить;
- сопоставить;
- создать как custom column;
- сохранить в import raw payload.

Название и иерархия групп должны сохраняться. Если Key Collector экспортировал путь одной строкой, пользователь задаёт separator и видит preview дерева.

В Web wizard доступен явный профиль Key Collector. Он автоматически
сопоставляет фразу, путь группы, целевой/релевантный URL и Wordstat-колонки
«База», `""` и `"!"`; позиции, поисковик, регион, даты, KEI, комментарии,
цветовые и служебные поля сохраняются через типизированные import targets либо
как custom columns. Неизвестная колонка не отбрасывается автоматически.

Нативный `.kc4` принимается как отдельный MIME/расширение и обрабатывается
только в import worker. Worker потоково проверяет ZIP central directory,
запрещает encrypted entries, path traversal, duplicate `main.tkc4`, zip bomb
и лишний executable payload, извлекает только точный `main.tkc4` во временный
mode-600 файл и открывает SQLite в read-only/query-only режиме с выключенным
trusted schema. Выполняется `quick_check`; SQL из проекта не исполняется.
Текущий лимит нативного файла — 1 GiB, максимум 32 archive entries, глубина
групп — 64, manifest — 20 000 активных путей. Иерархия `.kc4` строится по `ParentId`,
а не повторным разбором видимого пути или пользовательским separator, поэтому
глубокие деревья, одинаковые имена на разных уровнях и `/` внутри имени папки
не превращаются в плоские папки.
Публичная проекция дерева использует тот же предел 20 000, поэтому импорт из
5 000+ папок не превращает валидный SEO Data ответ в dependency error. Read
списка не ждёт group-tree advisory lock, если обе системные папки уже созданы;
во время длинного publish он видит последний committed snapshot дерева.
Текстовые значения SQLite читаются как raw BLOB: strict UTF-8 имеет приоритет,
для старых проектов разрешён Windows-1251 fallback. Строка с невосстановимым
replacement character не становится новым canonical keyword и фиксируется как
ошибка строки, поэтому повторный импорт не создаёт битые уникальные фразы.

Из `.kc4` импортируются только активные строки. Группы Key Collector с
признаком trash/removed и их запросы исключаются. Отдельный bounded manifest
групп сохраняет пустые папки и родителей, которых нет в keyword rows. Если
одна нормализованная фраза присутствует в нескольких активных группах,
publisher объединяет все её group paths, теги и custom values вместо выбора
первой строки. Публикация остаётся идемпотентной: manifest и объединённые
строки входят в hash каждого chunk command. Manifest также содержит валидные
hex-цвета активных групп; Core SEO применяет их к созданным и найденным папкам.
После чтения validated rows из JSONB publisher канонизирует порядок полей
вложенного SERP и текущей позиции до вычисления hash; его порядок совпадает с
повторным canonicalizer Core, поэтому порядок ключей, выбранный PostgreSQL, не
может вызвать ложный отказ публикации.
«Комментарий 1» и «Комментарий 2» объединяются в обычную заметку запроса и
одновременно остаются доступны исходными custom-полями. Комментарий группы
сохраняется как пользовательское поле у её запросов. Доступные
`KeywordGroupMetaTags`, признаки скрытия и наследования метатегов также
переносятся в bounded пользовательские колонки; отсутствие этих необязательных
таблиц или полей не останавливает импорт.

Для нативного `.kc4` Web по умолчанию выбирает `OVERWRITE_MAPPED`: повторный
импорт обновляет сопоставленные поля и заменяет членство уже существующих
запросов на фактические `ParentId`-пути проекта Key Collector. Это позволяет
без дублей исправить ранее импортированную плоскую структуру; несопоставленные
пользовательские данные не удаляются. Для CSV/XLSX остаётся явный выбор
политики дублей пользователем.

Создание отсутствующих в проекте запросов управляется отдельным флагом
`createMissingKeywords` («Добавлять новые запросы»). Доступный режим
универсального файла включает его по умолчанию; режим импорта позиций начинает
с безопасного обновления существующих строк. Профиль Key Collector доступен
для нативного `.kc4`; профиль Топвизора остаётся отключённым до отдельной
проверки совместимости.
При выключении нормализованная фраза и язык используются только для поиска
существующего запроса, а отсутствующие фразы показываются в validation preview
отдельным счётчиком. Web по умолчанию использует язык `ru`, как
и ручное создание запросов; пользователь может изменить его или сопоставить
явную колонку языка перед validation. Для старого уже подтверждённого mapping без
этого поля сохраняется прежнее create-enabled поведение, чтобы resume не менял
смысл выполняющегося импорта после обновления.

После успешного разбора нативного `.kc4` import worker сам сохраняет
канонический mapping Key Collector (`ru`, иерархия по `ParentId`,
`OVERWRITE_MAPPED`) и сразу ставит validation job. Известные поля получают
типизированные targets; каждая другая видимая колонка автоматически становится
уникально названной `LONG_TEXT` custom column. Служебные JSON-колонки истории
и SERP не публикуются как custom values: валидатор переносит их в immutable
rank snapshots и `rank_serp_results`. Поэтому API-импорт `.kc4` не зависит от
Web и не требует ручного назначения полей. Platform API передаёт worker
доверенный снимок semantic capacity при создании операции. Если серверный
mapping полон и validation нашла хотя бы один допустимый запрос, worker сразу
ставит публикацию: таблица preview и ручное подтверждение для нативного KC4 не
показываются. Legacy-операция без снимка лимитов безопасно остаётся на ручном
подтверждении; табличные форматы сохраняют обычный mapping/preview workflow.
Во время parsing/validation/publishing `semantic_imports.stage` содержит
bounded счётчики обработанных строк, а на публикации — номер chunk и общее
число chunks. Web показывает текущую фазу и числитель/знаменатель, сохраняет
активный import ID для повторного открытия и запрашивает подтверждение перед
закрытием работающего импорта. Publish batch ограничен 5 000 canonical строками
для табличных форматов и 1 000 строками для нативного KC4 с позициями,
историей и SERP. Более короткая KC4 transaction регулярно обновляет heartbeat
и укладывается в production timeout даже при создании большого числа
immutable snapshots.
Один `semanticImportPublishMaxRows=5000` используется отправителем и
принимающим Core API: расхождение со старым лимитом 500 недопустимо. Внутри
чанка custom values записываются пакетными `INSERT .. ON CONFLICT` через
`jsonb_to_recordset` блоками до 10 000 значений; неизменный конфликт не
переписывается и не увеличивает version. Manifest папок создаётся уровнями
дерева через `createMany`; по одному SQL-запросу на каждое поле или каждую
новую папку не выполняется.
Повторный `OVERWRITE_MAPPED` также обновляет существующие keywords одним
tenant-scoped `jsonb_to_recordset` batch вместо N отдельных ORM-команд.
Интерактивная транзакция одного крупного чанка ждёт свободное соединение до
30 секунд и ограничена пятью минутами, а
таймаут Jobs-клиента — 360 секундами, чтобы клиент не оборвал ещё допустимую
серверную транзакцию.
При повторном publish claim worker читает число уже принятых chunk из Core
receipt, восстанавливает cursor validated rows и продолжает со следующего
chunk. Повторная отправка всего префикса большого KC4 запрещена. Любой успешно
принятый chunk сбрасывает счётчик неудачных claims. Временная недоступность Core
оставляет импорт в `ready_to_publish` и не превращает сохранённые данные в
terminal failure; dispatcher создаёт только один следующий job без параллельных
BullMQ retries. `INVALID_COMMAND` при rolling смене версии Execution/Core имеет
окно до сорока последовательных claims без прогресса.

Перед hash и отправкой publisher повторно приводит payload к тем же ограничениям,
что принимающий Core: SERP title ограничен 2 048 символами, snippet — 8 192,
история — 1 100 измерениями, membership одного запроса — 100 группами. В legacy
KC4-ячейке с несколькими URL выбирается первый допустимый HTTP(S) URL; неверное
опциональное значение не отклоняет весь chunk.

Statement trigger, инвалидирующий проекцию графика позиций, обязан сначала
выбрать уникальные пары workspace/project из transition table и только затем
добавить volatile timestamp. Один KC4 chunk с тысячами rank snapshots изменяет
ревизию проекта один раз; `clock_timestamp()` не участвует в `DISTINCT`.
Повторный claim не очищает сохранённый progress. После чтения Core receipt
worker немедленно восстанавливает точные processed rows/chunks, а после
последнего chunk показывает отдельную фазу финализации при неизменных 100%.
Core даёт финализации 30 секунд на получение connection и до 300 секунд на
транзакцию. Timeout Jobs-команды `complete` равен 360 секундам, как у
насыщенного KC4 chunk.

Сохранённые в `.kc4` текущие и исторические позиции Яндекс и Google
импортируются в стандартный
immutable rank snapshot path и производный current-rank read model, а не
прямой записью в read model и не в произвольные custom columns. Технический
import context создаётся по полному сочетанию поисковика, страны, региона,
языка и устройства; текущие значения и история одной географии используют
один deterministic context. Переносятся found /
not-found, текущая и предыдущая позиция, даты истории и URL результата, если
эти данные присутствуют в проекте Key Collector. Доступные строки
`Module_SERP_Data` и `Module_SERP_Data_History` распаковываются в bounded Top-100 и сохраняются как
immutable `rank_serp_results`; повреждённый необязательный URL, title или
snippet либо текст длиннее DB-boundary `2048/8192` пропускается без остановки
остальных строк. Релевантные страницы
обоих поисковиков остаются доступными в отдельных пользовательских колонках.
Отсутствующая таблица конкретного поисковика не создаёт вымышленных значений.
Несколько записей одного поисковика за одну дату сворачиваются в один
согласованный замер. Найденная позиция имеет приоритет над `not-found`; итог
никогда не содержит одновременно `found=false` и число позиции. Дедупликация
выполняется и при validation, и перед publish для безопасного resume уже
подготовленного импорта. Регион и устройство извлекаются из task state Key
Collector отдельно для Яндекса и Google. Настройка конкретной папки имеет
приоритет, затем применяется ближайшая настройка предка и только затем default.
Яндекс LR разрешается штатным каталогом регионов, Google canonical location —
фиксированным проверяемым snapshot каталога кодов. Timestamp scheduler для
текущей позиции нормализуется к существующему историческому измерению того же
дня, поэтому текущий SERP не создаёт второй срез рядом с историей. Publisher
после чтения JSONB повторно валидирует и сохраняет весь current-position
context вместе с SERP; контекстные поля не могут быть отброшены между
validation и Core publish. При повторном `OVERWRITE_MAPPED` snapshot той же
даты обновляет mutable `current_ranks`; существующая проекция восстанавливается
на последнюю дату с предпочтением снимка, у которого есть SERP. Сами
`rank_snapshots` и `rank_serp_results` остаются immutable.
Домен проекта берётся из доверенного tenant/project snapshot при создании
импорта и входит в hash publish-команды, поэтому imported SERP поддерживает
поиск всех URL проекта. Технический import context не
показывается как настраиваемый или запускаемый профиль live-съёма, не входит в
квоту отслеживаемых пар и не может быть изменён через пользовательские
tracking-context команды. Импортированные snapshots при этом остаются
доступны через keyword insights, полный SERP-history endpoint, график и общий
`rank-workbench/serp` с явной пометкой Key Collector. Workbench читает
канонические `rank_snapshots/rank_serp_results` и конечный provider enum,
поэтому frontend не различает имена таблиц, модулей и полей исходного `.kc4`.
После успешной публикации с реальной географией Core
архивирует прежние технические `global`/`kc4-import` contexts и удаляет только
их из активной read-проекции по статусу контекста; current-rank и исходные
immutable снимки физически сохраняются как audit evidence.
Каталог доступных rank-срезов начинает чтение с малой таблицы
`tracking_context_versions` и для каждой конфигурации выполняет индексный
`LATERAL .. LIMIT 1` probe в `rank_snapshots`. Он не делает `DISTINCT`-скан
сотен тысяч импортированных snapshots при каждом открытии Семантики.

В mapping wizard табличных форматов позиции, изменение и релевантный URL Яндекс и Google имеют
раздельные назначения с логотипами поисковиков. Также отдельно доступны язык,
приоритет, избранное, отслеживание, заметка и интент. Пользователь может отключить любую исходную
колонку. Для нативного KC4 этот mapping является серверным профилем и не
редактируется вручную; нестандартные CSV/XLSX остаются полностью настраиваемыми.

Основная таблица семантики и таблица позиций строятся одним grid-компонентом.
Обе поддерживают server-side сортировку по трём частотностям и позициям,
project-shared порядок/видимость колонок и отдельные релевантные URL Яндекс и
Google из результата съёма.

## 18. Import wizard

### Шаг 1. Источник

Web даёт выбрать `Key Collector`, `Файл` или `Позиции`. Нативный Key Collector
принимает только `.kc4` до 1 GiB; `Топвизор` находится внизу полноразмерной
левой панели и явно disabled как временно недоступный; источник `Вручную`
удалён из import wizard. Обычный список запросов добавляется
штатным действием «Добавить» в Семантике. Справочный блок закреплён у нижнего
края панели и ведёт на локализованную страницу `/{locale}/imports`. Выбор
доступного источника меняет допустимые расширения, автоматический mapping,
подсказку и примеры, но не обходит общую антивирусную проверку, staging и
validation. Нативный KC4 после них публикуется автоматически; для табличных
форматов остаётся явное подтверждение. На desktop правая часть
прокручивается независимо, поэтому навигация и документация остаются видимыми.

- upload;
- clipboard;
- integration;
- recent file.

### Шаг 2. Формат

- encoding;
- delimiter;
- sheet;
- header;
- locale;

## 19. Архитектура импорта

1. Клиент получает multipart upload session.
2. Части загружаются напрямую в S3-compatible storage. Если preview/VPS
   публикует object storage на отдельном порту того же хоста, который
   недоступен клиентской сети, Web переключает только этот allowlisted origin
   на потоковый same-origin relay: signed URL остаётся серверным заголовком,
   тело не буферизуется, произвольный upstream/redirect запрещён.
3. Завершение upload сверяет состав parts и фактический размер объекта.
4. Worker потоково вычисляет SHA-256, сверяет переданный клиентом checksum,
   если он был указан, и выполняет антивирусную проверку.
5. Parser job читает потоково.
6. Строки попадают в staging tables.
7. Для табличных форматов пользователь проверяет предложенный mapping, язык,
   разделитель пути групп, merge policy и отдельное разрешение создавать
   отсутствующие запросы; сохранение mapping переводит import в `validating`.
   Для нативного `.kc4` parser атомарно сохраняет полный серверный mapping и
   переводит import в `validating`; Web не участвует в выборе полей.
8. Validation job нормализует запросы через `seo-data` и создаёт безопасный
   summary. Табличный импорт переходит в `awaiting_confirmation`; нативный KC4
   с полным серверным mapping и сохранённым entitlement — сразу в
   `ready_to_publish`.
9. Для табличного формата пользователь подтверждает validation preview. Для
   KC4 worker сам ставит publish job. Commit выполняет chunked merge через
   внутренний API владельца semantic core.
10. Создаются semantic version, audit и результат.

Требования:

- файл не загружается целиком в память;
- parser worker читает CSV/TSV как `AsyncIterable`, буферизует для определения
  формата не более 64 КиБ и сохраняет строки пакетами не более 5000 записей;
- первая реализация CSV/TSV поддерживает UTF-8/UTF-8 BOM/Windows-1251,
  запятую/точку с запятой/tab, quoted CRLF и quoted multiline fields;
- parser job имеет отдельный атомарный lease/heartbeat и безопасно
  переигрывается: перед повторным разбором staging данного import очищается,
  а уникальность `(import_id, row_number)` не допускает дублей; BullMQ-lock
  worker должен жить не меньше 30-минутного DB lease, поскольку нативный
  SQLite parser может дольше стандартных 30 секунд занимать event loop;
- staging принадлежит `jobs_db`, hash-partitioned по `import_id`; публикация
  канонических Keywords выполняется только через внутренний контракт
  `seo-data`, без прямого доступа к его БД;
- validation staging хранится отдельно от raw staging, также partitioned по
  `import_id`; canonical row содержит только allowlisted нормализованные поля,
  issue codes и признак существующего запроса; при update-only импорте
  publisher выбирает только строки с этим признаком, а semantic core повторно
  запрещает создание отсутствующей строки на случай конкурентного изменения;
- `seo-data` проверяет tenant/actor context одновременно по trusted headers и
  body, повторно валидирует каждую строку и не доверяет типам jobs-сервиса;
- каждый commit chunk имеет стабильный индекс и SHA-256 payload; receipt
  `(import_id, chunk_index)` делает повторную доставку идемпотентной и
  отклоняет подмену payload под уже использованным индексом;
- публикация сериализуется advisory lock по project, а финализация создаёт
  ровно одну `SemanticVersion`; повтор complete возвращает прежний результат;
- неизвестные колонки и исходные значения не теряются: они сохраняются в
  `raw_values`, а нативный KC4 mapping превращает их в custom columns;
- `GET /projects/{projectId}/imports/{importId}/preview-rows` читает staging
  cursor-страницами ровно по 100 строк. Cursor связан с сортируемой колонкой и
  направлением; смена сортировки начинает новую страницу. UI подгружает
  следующую сотню у нижней границы внутреннего scroll, показывает фактическое
  количество строк и не переносит крупные служебные KC4 JSON-ячейки в ответ;
- resume начинает чтение с первого отсутствующего chunk receipt и не повторяет
  уже принятую часть validated набора;
- клиентский checksum опционален, чтобы браузер не читал многогигабайтный
  файл целиком; серверный SHA-256 обязателен до статуса `ready`;
- inspection выполняется отдельным масштабируемым worker process через
  идемпотентную BullMQ queue; queue payload содержит только `upload_id`;
- worker получает upload lease атомарно, обновляет heartbeat и повторно
  подбирает зависшие `scanning` записи после истечения lease;
- весь поток без выборочного пропуска передаётся в ClamAV INSTREAM, а первые
  ограниченные байты используются только для проверки container signature и
  фактического MIME;
- `StreamMaxLength`, `MaxScanSize` и `MaxFileSize` ClamAV не могут быть ниже
  публичного upload limit. Для текущего предела 5 GiB все три scanner limits
  равны 5 GiB; иначе крупный KC4 ошибочно зацикливается в retryable inspection;
- scanner работает fail-closed: при недоступных S3/ClamAV upload возвращается
  в `uploaded` с retryable техническим состоянием и никогда не становится
  `ready`;
- malware, несовпадение размера/checksum и подмена типа переводят upload в
  `rejected`; parser и download URL для такого объекта запрещены;
- UI получает текущее состояние через project-scoped read endpoint и может
  безопасно повторять polling до terminal state;
- после появления preview табличного импорта modal разворачивается почти на весь viewport;
  таблица прокручивается по обеим осям внутри собственной области, header
  остаётся sticky, а каждая исходная колонка запускает серверную сортировку
  полного staging набора как число либо текст. Назначение поля и имя
  custom-колонки образуют один ровный header-блок, общие правила публикации
  находятся ниже и доступны через scroll всей рабочей области. После parsing
  загрузочный dropzone, source navigation, progress bar и текст про первичную
  проверку скрываются как уже не относящиеся к текущему шагу;
- нормализация перед validation передаёт до 5 000 строк одним tenant-scoped
  запросом с отдельным body/response limit 32 MiB. Это сокращает число HTTP
  round trips в десять раз и не меняет batch/chunk limits самой публикации;
- commit идемпотентен;
- повтор job не создаёт дубли;
- progress отражает bytes, rows и stage;
- отмена до commit безопасна;
- отмена commit завершает текущую транзакцию chunk и прекращает следующие;
- импорт может завершиться частично; crash после `cancel_requested`
  восстанавливается dispatcher-ом, а уже применённые chunks фиксируются
  отдельной partial semantic version;
- row-level errors экспортируются.

Состояния первой рабочей реализации:

Табличный путь:
`queued → parsing → awaiting_mapping → validating → awaiting_confirmation → ready_to_publish → publishing → completed`.
Нативный KC4 с доверенным entitlement пропускает оба пользовательских шага:
`queued → parsing → validating → ready_to_publish → publishing → completed`.
Если возобновляется legacy-операция без entitlement snapshot, после validation
она остаётся в `awaiting_confirmation`, чтобы не обходить capacity boundary.

Из `parsing`, `validating` и `publishing` worker восстанавливает просроченный
lease. Отмена до `publishing` является немедленной; во время `publishing` —
кооперативной. Терминальные состояния: `completed`, `failed`, `cancelled`.

Любой инструмент сначала показывает preview и количество затронутых строк.

Поиск неявных дублей сравнивает мультимножество слов независимо от их порядка,
сохраняя количество повторов каждого слова. Поддерживаются точный и
улучшенный русскоязычный формонезависимый режимы, отдельный учёт регистра и
пунктуации, а также список исключаемых слов. Умная отметка детерминированно
оставляет по одной фразе с максимальной базовой частотностью, приоритетом или
самой ранней датой добавления. Preview фиксирует версии удаляемых фраз и
оставляемого варианта и возвращает все группы страницами по 100 с единым
стабильным hash. Web автоматически догружает страницы при прокрутке и
накапливает группы без ручной навигации. Каждая строка показывает полный текст,
все папки и последние базовую, фразовую и точную частотности с маркером Яндекса;
одна серверная страница содержит не больше 500 кандидатов на удаление, поэтому
чрезмерно большая группа явно помечается как усечённая. Scope анализа можно
задать всем проектом, optimistic selection либо union до 2 000 выбранных папок.
Выбор родителя включает только его прямые запросы. Отдельная кнопка
«Вложенные» добавляет потомков и отмечает их; один запрос с несколькими
подходящими membership участвует в анализе один раз. Пользователь включает
нужные группы дублей и может переопределить оставляемый запрос; применение принимает
только эти решения, разбивает большой пользовательский выбор на обратимые
пакеты до 500 строк, переносит их в системную корзину и не выполняет permanent
delete. Непросмотренные и пропущенные группы не изменяются.

Минус-слова поддерживают проектные пресеты до 1 200 строк. Дополнительно Web
предлагает read-only стандартные шаблоны: полный уникальный список названий
городов России в одном пресете, объединённый пресет всех городов и регионов,
отдельный набор регионов, а информационный спрос, бесплатные загрузки, работа
и доски объявлений — в узкие необязательные наборы. Шаблон никогда не применяется
автоматически: пользователь видит его описание, может изменить строки,
выполнить preview и сохранить отдельной копией в проект. Поддерживаются пять
режимов поиска:
быстрое либо улучшенное русскоязычное сопоставление без учёта словоформ,
полное вхождение слова/фразы с учётом словоформы, частичное вхождение и точное
совпадение всей фразы от начала до конца. Для стоп-фраз из двух и более слов
можно независимо игнорировать порядок слов, пунктуацию и специальные символы;
регистр остаётся отдельной опцией. Scope задаётся всем проектом, optimistic
selection либо union до 2 000 выбранных папок. Выбранный родитель включает
только свою папку; потомки добавляются отдельной кнопкой «Вложенные» и явно
отмечаются в дереве. Запрос с несколькими подходящими membership проверяется
один раз. Public и trusted boundaries принимают canonical `groupIds`, сохраняя
legacy single `groupId` только для rolling deployment. Preview возвращает
число проверенных/совпавших строк, hash и постраничный список всех совпадений
по 100 строк. Web автоматически запрашивает следующую страницу при прокрутке,
накапливает уже просмотренные строки и не показывает селектор размера либо
ручную навигацию. Каждое совпадение содержит UTF-16 диапазоны, чтобы Web
подсвечивал найденное слово непосредственно внутри текста запроса без
дублирующей подписи. Все совпадения по умолчанию отмечены для перемещения;
пользователь может снять отметку у отдельных загруженных строк, и эти exact
keyword ID остаются активными во всех последующих пакетах применения.
Счётчики и подтверждающая кнопка показывают только реально выбранные строки.
Применение требует тот же hash и версии строк, переносит выбранные запросы в
системную корзину пакетами до 500 строк, возвращает точные ID
перемещённых запросов и создаёт обратимую semantic version. Без успешного
preview удаление запрещено.

## 25. Детальная карточка запроса

Правая карточка использует пять верхних вкладок: `Обзор`, `Позиции`,
`Выдача`, `Wordstat` и `Заметка`. `Позиции` и `Выдача` внутри разделены на
`SEO выдача` и `ИИ выдача`; ИИ-переключатель полностью скрыт, пока по ключу не
существует ни одного сохранённого ИИ-снимка.

`Обзор` показывает параметры запроса, bounded список всех его текущих папок с
цветами групп, целевой URL и состояние данных с быстрыми переходами в
соответствующие вкладки. `Позиции` содержит текущие
значения, график, последние изменения и историю. `Выдача` показывает
сохранённые organic SERP либо источники ИИ. `Wordstat` объединяет три вида
частотности, сохранённые срезы и сезонность. `Заметка` предоставляет отдельный
редактор и предупреждает перед закрытием при несохранённых изменениях.

В `Позициях` и `Выдаче` используются независимые селекты срезов. Для SEO в них
доступны только точные сочетания поисковика, города и устройства с
соответствующими rank/SERP-данными. Для ИИ доступны только сочетания с
ИИ-позицией либо источниками; селект самой ИИ-выдачи содержит только снимки с
сохранёнными источниками. Выбор одного раздела не подменяет срез в другом.
Карточка загружает bounded проекцию всех доступных срезов ключа. Правила
`rank_dimension_merges` применяются и к общему ответу без выбранного среза,
поэтому источник исчезает из селекта, а его текущая позиция и SERP проецируются
на целевой dimension. Цепочки объединений разрешаются до конечного target;
история конечного среза включает все прямые и транзитивные source dimensions,
а цикл считается повреждением storage. Фильтрация
выбранного города и устройства выполняется внутри карточки без повторного
запроса и без смешивания SEO- и ИИ-данных. Нижняя граница keyword-scoped SERP
history не берётся из `Keyword.createdAt`: импортированный KC4 snapshot может
быть старше созданной при переносе записи. Полный диапазон остаётся bounded
точным keyword/dimension и cursor-страницей по 5 снимков.
Активная верхняя вкладка, единый режим SEO/ИИ для вкладок `Позиции` и
`Выдача`, а также четыре независимых выбранных среза сохраняются локально по
пользователю, проекту и представлению. Переключение `Позиции → Выдача`
сохраняет SEO/ИИ-режим. Если у очередного ключа нет ИИ-снимков, карточка
временно показывает SEO и скрывает ИИ-переключатель, не затирая сохранённый
выбор; на следующем подходящем ключе восстанавливается ИИ.

`Заметка` редактируется как обычный текст в одном компактном `textarea` без
панели Markdown-форматирования. Сохранение и защита от случайного закрытия
несохранённого текста остаются обязательными.

У заметки запроса нет отдельного продуктового ограничения длины; общий
transport body limit по-прежнему ограничивает HTTP-запрос. В табличной
проекции передаётся только признак её наличия, а текст читается в
tenant-scoped карточке.
В карточке блок частотности расположен после блоков SERP-конкурентов и перед
заметкой. У каждого показанного контекста type/region/device есть компактная
кнопка удаления. Действие требует отдельного modal-подтверждения и удаляет все
сохранённые snapshots этого контекста только у выбранного keyword, чтобы после
удаления не подставлялся более старый срез; команда защищена `semantic.update`,
CSRF, mutable-project и tenant scope и фиксируется в аудите.
График позиций строится из append-only rank snapshots отдельно по tracking
context/search engine. Отсутствие позиции разрывает сплошную линию, выводится
на отдельной оси «нет» и соединяется с соседними замерами только пунктиром —
оно не подменяется нулём или предельной позицией. График остаётся видимым и
когда все доступные замеры имеют состояние `not found`: вместо пустого блока
он показывает сохранённые кресты на оси «нет». Наведение и клавиатурный
фокус притягиваются к ближайшему замеру и показывают позицию, точные дату и
время, поисковую систему и источник выдачи, provider, регион, устройство,
глубину и название tracking context. В таблице основное число является
текущей позицией, а рядом выводится изменение относительно предыдущей
найденной позиции: зелёное `▲N`, красное `▼N`, `—` без изменений или
«Новая». Если свежий замер не нашёл позицию, показывается `×` и «Была N».
В карточке текущие значения Яндекса и Google стоят в одной компактной строке:
цифра означает найденную позицию, `×` — потерянную, `—` — отсутствие данных;
дублирующие подписи «Не найдена» и «Нет данных» не выводятся. Обычный график и
его список изменений находятся внутри блока обычных позиций, а отдельный
ИИ-график — только внутри блока ИИ-позиций.
Клик по строке переносит табличный фокус в карточку запроса. `ArrowUp` и
`ArrowDown` переключают соседние уже загруженные строки без закрытия карточки;
с зажатым `Shift` диапазон выделяется по тем же правилам, что Shift-клик.
Под графиком показываются пять последних календарных дат текущих контекстов
Яндекса и Google, а полный список открывается отдельным modal. Для последнего
XMLStock snapshot каждого поисковика карточка показывает первые пять из
сохранённых Top-10 organic результатов и раскрывает остальные по действию
«Показать все». Если назначенный target URL не совпадает с текущим ranking URL
после нормализации host/path, карточка явно показывает найденную страницу и
предупреждение, не изменяя target URL автоматически.
Новые частотности и позиции появляются в открытой таблице через
reconciliation текущей HTTP-проекции по изменению progress, без перезагрузки
страницы; WebSocket не является источником истины.

## 26. Состояния и ошибки модуля

- ядро пусто;
- импорт готовится;
- импорт требует mapping;
- импорт в процессе;
- импорт частично успешен;
- данные индексируются;
- custom formula пересчитывается;
- кластеризация proposal ready;
- bulk operation running;
- row conflict;
- source context missing;
- stale metrics;
- group counts recalculating;
- project archived;
- permission restricted;
- plan limit reached;
- storage limit reached.

## 27. Критерии производительности

- Вычисление предыдущей позиции для страницы связывает текущий snapshot по
  обеим частям составного ключа `(observed_at, id)`. Поиск только по `id` при
  известном времени запрещён: после импорта большой истории он превращает
  bounded page в тысячи неполных index scan.
- Сортировка по позиции сначала ограничивает предыдущую историю совместимыми
  tracking contexts и использует индекс keyword/context/time. Для найденной
  текущей позиции historical lookup не выполняется, поскольку он не влияет на
  её sort bucket.
- Все тяжёлые bounded reads семантики (`keywords`, body list/search,
  operation scope и агрегаты графика) имеют согласованные границы: 30 секунд
  между Platform API и SEO Data и 35 секунд в BFF. Это аварийные пределы для
  холодного cache miss, а не целевая задержка интерфейса; остальные API не
  получают неограниченный timeout.
- Проектная история позиций хранит persistent revisioned projection. После
  первого расчёта совпадающий scope не сканирует `rank_snapshots` повторно;
  завершение импорта/съёма прогревает новую revision.
- Открытие таблицы не должно загружать весь набор.
- p95 первого блока до 500 строк — не более 1,5 секунды при прогретом кеше.
- Фильтр по индексируемым полям — p95 не более 1 секунды.
- Scroll виртуализированной таблицы — целевые 60 fps на поддерживаемом устройстве.
- Inline update подтверждается UI не позднее 300 мс optimistic state; серверный p95 — до 500 мс.
- Импорт 5 ГБ принимается без HTTP timeout и продолжает обработку после закрытия вкладки.
- Bulk operation по миллионам строк не удерживает длинную HTTP-транзакцию.

## 28. Заметки, сезонность и переход к отчёту позиций

У `Keyword.note` нет отдельного продуктового ограничения длины: storage остаётся
PostgreSQL `text`, а общий HTTP body limit ограничивает транспорт. В списке
передаётся только `hasNote`; полный текст читается через insights и изменяется
по `If-Match`, поэтому icon-modal не может затереть параллельное изменение.

Keyword insights дополнительно возвращает последний набор сезонных точек для
каждого сочетания granularity/region/device. Таблица семантики не загружает эти
ряды для всех ключей: график появляется только в открытом инспекторе. Основной
отчёт по датам находится на отдельном `/app/rankings`, но использует те же
keyword IDs, папки и полную modal истории.
