# Семантическое ядро, импорт и совместимость с Key Collector

## 1. Назначение

Модуль является основным рабочим инструментом SEO-специалиста и должен поддерживать миллионы запросов, массовые операции, историю, совместную работу и обогащение внешними данными.

### 3.3. Загрузка таблицы и поиск

- Первичное чтение опубликованного ядра выполняется через
  `GET /projects/{projectId}/keywords`; frontend не обращается к `seo-data`
  напрямую.
- Обязательна стабильная keyset/cursor pagination по `created_at DESC, id DESC`;
  offset pagination для больших ядер не используется.
- Размер страницы по умолчанию — 100, максимум — 1 000 строк. Пользователь
  выбирает размер блока infinite scroll из 100, 200, 500 или 1 000 строк;
  выбор сохраняется отдельно для проекта в локальных layout-настройках.
- Cursor связан с нормализованным поисковым запросом и не принимается при
  изменении фильтра.
- Подстрочный поиск выполняется по нормализованному тексту и использует
  trigram-индекс.
- Первая страница может возвращать `totalApprox`; последующие страницы не
  должны повторять дорогой `count`.
- Начальный read model строки включает оригинальный и нормализованный текст,
  язык, tracking-флаг, основную группу, target URL, первые 10 тегов, источник,
  даты и версию. Расширенные метрики добавляются отдельными projections.
- UI обязан различать initial loading, empty core, empty search result,
  recoverable error, loading next page и normal state. На узких экранах
  таблица прокручивается внутри контейнера и не расширяет документ.
- Заголовок grid и настроенный порядок колонок остаются видимыми при пустом
  проекте, пустой выбранной группе и пустом результате поиска/фильтров;
  empty-state показывается внутри тела уже смонтированной таблицы.
- Пустая выбранная группа не считается пустым результатом фильтра: UI сообщает,
  что в группе ещё нет запросов, и предлагает открыть ручное добавление сразу с
  этой группой. Корневая группа «Все запросы» с нулевым счётчиком показывает
  аналогичное состояние проекта и ручное добавление без выбранной группы. Для
  системной корзины действие добавления не показывается.
- Применение фильтров и серверной сортировки обновляет строки внутри уже
  смонтированной таблицы, не перезагружает страницу и сохраняет допустимую
  позицию внутреннего scroll-контейнера. Предыдущие строки остаются видимыми до
  получения нового ответа; loading-state не должен изменять геометрию экрана.
- Позиция поисковика показывается одной колонкой с логотипом, текущим значением
  и компактным предыдущим значением. Рост и падение различаются цветом и
  текстовой подписью; отдельная колонка с символом delta не используется.
- При сортировке по позиции найденные значения всегда идут раньше отсутствующих
  независимо от направления сортировки. Если свежий съём не нашёл позицию, но
  предыдущее найденное значение известно, ячейка показывает `×` и `было N`.
- Проекции Wordstat обозначаются как «База», `""` и `"!"`; заголовки содержат
  доступный маркер Яндекса и не повторяют слово «частотность» в каждой колонке.

## 6. Дедупликация

Режимы:

- точное совпадение оригинала;
- совпадение normalized;
- без учёта операторов;
- без учёта порядка слов;
- по леммам;
- пользовательская формула.

Действия при дубле:

- пропустить;
- объединить значения по правилам;
- заменить существующую строку;
- создать вариант;
- отправить в отдельную группу конфликтов.

При объединении пользователь видит, какие поля будут сохранены, перезаписаны или конфликтуют.

### 6.1. Ручное массовое добавление

- Один пользовательский запуск принимает до 2 000 строк; Web отправляет их
  последовательными chunk по 100 строк, сохраняя исходный индекс каждой строки.
- Команда первичного добавления явно передаёт `duplicatePolicy`:
  `SKIP_EXISTING` или `REJECT_EXISTING`. Активное совпадение никогда не
  создаётся повторно. Совпадение в «Корзине» также не восстанавливается молча:
  строка получает признак `trashed`, а Web после завершения добавления
  открывает отдельную таблицу с checkbox для явного выбора восстановления.
- Только строки, подтверждённые в этой таблице, повторно отправляются с
  внутренним явным действием `RESTORE_TRASHED`. Для импорта действует тот же
  порядок: завершённый import receipt возвращает bounded список совпадений из
  «Корзины», после чего пользователь выбирает восстанавливаемые запросы в
  следующем modal. Отмена не изменяет «Корзину».
- `SKIP_EXISTING` возвращает `SKIPPED_EXISTING`, а `REJECT_EXISTING` —
  row-level `REJECTED_EXISTING`; остальные строки одного запуска продолжают
  обрабатываться.
- Устаревшая `DELETED`-запись без членства в «Корзине» восстанавливается тем же
  ID через tenant-scoped CAS, получает новое членство/теги и не резервирует
  дополнительную stored capacity. Новый нормализованный ключ создаётся только
  после проверки workspace/project capacity.
- Ответ содержит `selected/created/restored/skipped/rejected/failed` и ровно
  один индексированный outcome на входную строку. Тексты запросов и секреты в
  ответ, audit и внутренние логи не копируются.
- Только bulk-create routes принимают body до 8 MiB; валидатор ограничивает
  сериализованный payload шестью MiB. Остальные API routes сохраняют штатный
  меньший лимит.

## 7. Группы

- Иерархия без фиксированной глубины, но UI оптимизирован до 10 уровней.
- Группа имеет название, цвет, родителя, sort order, описание и владельца.
- Запрос может находиться в нескольких группах; таблица показывает выбранную
  группу в текущем контексте, а импорт не теряет остальные членства.
- Дополнительная классификация выполняется тегами.
- Перемещение большой группы — асинхронная операция.
- В каждом проекте существуют защищённые системные группы «Без группы» и
  «Корзина»: их нельзя переименовать, вложить в другую папку или удалить.
- Активный запрос без обычной группы автоматически состоит в «Без группы».
- Обычное удаление запроса переносит его в «Корзину»; необратимое удаление
  разрешено только из неё. Оно уничтожает пользовательский текст, членства,
  теги и custom values и освобождает уникальную нормализованную identity.
  Непрозрачный технический tombstone сохраняется только для неизменяемой
  исторической provenance позиций и не отображается как запрос проекта.
- При удалении дерева групп checkbox «Переместить запросы в корзину» выключен
  по умолчанию. В этом режиме членства удаляемого дерева снимаются, а запросы
  без другого членства переходят в «Без группы». Включённый checkbox переносит
  все запросы дерева в «Корзину».
- Количество запросов пересчитывается асинхронно и допускает временный `calculating`.

### 17.3. Key Collector

Поддерживается импорт CSV/TSV/XLSX, экспортированных из Key Collector, и
нативного проекта `.kc4`.

Wizard должен распознавать и предлагать mapping:

- фраза;
- группа и иерархия групп;
- базовая/точная/фиксированная частотность;
- регионы;
- позиции;
- релевантная страница;
- поисковая система;
- дата проверки;
- теги/цветовые маркеры;
- KEI и пользовательские показатели;
- служебные колонки;
- пользовательские колонки.

Неизвестные колонки:

- можно пропустить;
- сопоставить;
- создать как custom column;
- сохранить в import raw payload.

Название и иерархия групп должны сохраняться. Если Key Collector экспортировал путь одной строкой, пользователь задаёт separator и видит preview дерева.

В Web wizard доступен явный профиль Key Collector. Он автоматически
сопоставляет фразу, путь группы, целевой/релевантный URL и Wordstat-колонки
«База», `""` и `"!"`; позиции, поисковик, регион, даты, KEI, комментарии,
цветовые и служебные поля сохраняются через типизированные import targets либо
как custom columns. Неизвестная колонка не отбрасывается автоматически.

Нативный `.kc4` принимается как отдельный MIME/расширение и обрабатывается
только в import worker. Worker потоково проверяет ZIP central directory,
запрещает encrypted entries, path traversal, duplicate `main.tkc4`, zip bomb
и лишний executable payload, извлекает только точный `main.tkc4` во временный
mode-600 файл и открывает SQLite в read-only/query-only режиме с выключенным
trusted schema. Выполняется `quick_check`; SQL из проекта не исполняется.
Текущий лимит нативного файла — 1 GiB, максимум 32 archive entries, глубина
групп — 64, manifest — 2 000 путей. Иерархия `.kc4` строится по `ParentId`,
а не повторным разбором видимого пути или пользовательским separator, поэтому
глубокие деревья и одинаковые имена на разных уровнях не превращаются в
плоские папки.

Из `.kc4` импортируются только активные строки. Группы Key Collector с
признаком trash/removed и их запросы исключаются. Отдельный bounded manifest
групп сохраняет пустые папки и родителей, которых нет в keyword rows. Если
одна нормализованная фраза присутствует в нескольких активных группах,
publisher объединяет все её group paths, теги и custom values вместо выбора
первой строки. Публикация остаётся идемпотентной: manifest и объединённые
строки входят в hash каждого chunk command.

Для нативного `.kc4` Web по умолчанию выбирает `OVERWRITE_MAPPED`: повторный
импорт обновляет сопоставленные поля и заменяет членство уже существующих
запросов на фактические `ParentId`-пути проекта Key Collector. Это позволяет
без дублей исправить ранее импортированную плоскую структуру; несопоставленные
пользовательские данные не удаляются. Для CSV/XLSX остаётся явный выбор
политики дублей пользователем.

После успешного разбора нативного `.kc4` Web предлагает канонический профиль
Key Collector (`ru`, иерархия по `ParentId`, `OVERWRITE_MAPPED`), но не
запускает validation автоматически. Пользователь видит все исходные колонки,
может изменить назначение каждой из них или выбрать «Не импортировать», затем
явно запускает проверку и подтверждает validation preview.

Сохранённые в `.kc4` позиции Яндекс и Google импортируются в стандартный
immutable rank snapshot path и производный current-rank read model, а не
прямой записью в read model и не в произвольные custom columns. Для каждого
поисковика создаётся отдельный технический import context; переносятся found /
not-found, текущая и предыдущая позиция и URL результата, если эти данные
присутствуют в проекте Key Collector. Отсутствующая таблица конкретного
поисковика не создаёт вымышленных значений.

В mapping wizard позиции, изменение и релевантный URL Яндекс и Google имеют
раздельные назначения с логотипами поисковиков. Также отдельно доступны язык,
приоритет, избранное и интент. Пользователь может отключить любую исходную
колонку; нативный KC4 preset остаётся только стартовой настройкой и не
отменяет сделанный пользователем выбор.

Основная таблица семантики и таблица позиций строятся одним grid-компонентом.
Обе поддерживают server-side сортировку по трём частотностям и позициям,
project-shared порядок/видимость колонок и отдельные релевантные URL Яндекс и
Google из результата съёма.

## 19. Архитектура импорта

1. Клиент получает multipart upload session.
2. Части загружаются напрямую в S3-compatible storage. Если preview/VPS
   публикует object storage на отдельном порту того же хоста, который
   недоступен клиентской сети, Web переключает только этот allowlisted origin
   на потоковый same-origin relay: signed URL остаётся серверным заголовком,
   тело не буферизуется, произвольный upstream/redirect запрещён.
3. Завершение upload сверяет состав parts и фактический размер объекта.
4. Worker потоково вычисляет SHA-256, сверяет переданный клиентом checksum,
   если он был указан, и выполняет антивирусную проверку.
5. Parser job читает потоково.
6. Строки попадают в staging tables.
7. Для табличных форматов пользователь проверяет предложенный mapping, язык,
   разделитель пути групп и merge policy; сохранение mapping переводит import
   в `validating`. Для нативного `.kc4` Web предлагает тот же редактируемый
   mapping и не пропускает ручное подтверждение состава импортируемых полей.
8. Validation job нормализует запросы через `seo-data`, создаёт безопасный
   summary и переводит import в `awaiting_confirmation`.
9. Пользователь подтверждает validation preview; commit job выполняет
   chunked merge через внутренний API владельца semantic core.
10. Создаются semantic version, audit и результат.

Требования:

- файл не загружается целиком в память;
- parser worker читает CSV/TSV как `AsyncIterable`, буферизует для определения
  формата не более 64 КиБ и сохраняет строки пакетами не более 5000 записей;
- первая реализация CSV/TSV поддерживает UTF-8/UTF-8 BOM/Windows-1251,
  запятую/точку с запятой/tab, quoted CRLF и quoted multiline fields;
- parser job имеет отдельный атомарный lease/heartbeat и безопасно
  переигрывается: перед повторным разбором staging данного import очищается,
  а уникальность `(import_id, row_number)` не допускает дублей;
- staging принадлежит `jobs_db`, hash-partitioned по `import_id`; публикация
  канонических Keywords выполняется только через внутренний контракт
  `seo-data`, без прямого доступа к его БД;
- validation staging хранится отдельно от raw staging, также partitioned по
  `import_id`; canonical row содержит только allowlisted нормализованные поля,
  issue codes и признак существующего запроса;
- `seo-data` проверяет tenant/actor context одновременно по trusted headers и
  body, повторно валидирует каждую строку и не доверяет типам jobs-сервиса;
- каждый commit chunk имеет стабильный индекс и SHA-256 payload; receipt
  `(import_id, chunk_index)` делает повторную доставку идемпотентной и
  отклоняет подмену payload под уже использованным индексом;
- публикация сериализуется advisory lock по project, а финализация создаёт
  ровно одну `SemanticVersion`; повтор complete возвращает прежний результат;
- неизвестные колонки и исходные значения не теряются: до подтверждения
  mapping они сохраняются в `raw_values`, а UI показывает предложенное
  сопоставление и ограниченный sample;
- поддерживается resume;
- клиентский checksum опционален, чтобы браузер не читал многогигабайтный
  файл целиком; серверный SHA-256 обязателен до статуса `ready`;
- inspection выполняется отдельным масштабируемым worker process через
  идемпотентную BullMQ queue; queue payload содержит только `upload_id`;
- worker получает upload lease атомарно, обновляет heartbeat и повторно
  подбирает зависшие `scanning` записи после истечения lease;
- весь поток без выборочного пропуска передаётся в ClamAV INSTREAM, а первые
  ограниченные байты используются только для проверки container signature и
  фактического MIME;
- scanner работает fail-closed: при недоступных S3/ClamAV upload возвращается
  в `uploaded` с retryable техническим состоянием и никогда не становится
  `ready`;
- malware, несовпадение размера/checksum и подмена типа переводят upload в
  `rejected`; parser и download URL для такого объекта запрещены;
- UI получает текущее состояние через project-scoped read endpoint и может
  безопасно повторять polling до terminal state;
- commit идемпотентен;
- повтор job не создаёт дубли;
- progress отражает bytes, rows и stage;
- отмена до commit безопасна;
- отмена commit завершает текущую транзакцию chunk и прекращает следующие;
- импорт может завершиться частично; crash после `cancel_requested`
  восстанавливается dispatcher-ом, а уже применённые chunks фиксируются
  отдельной partial semantic version;
- row-level errors экспортируются.

Состояния первой рабочей реализации:

`queued → parsing → awaiting_mapping → validating → awaiting_confirmation → ready_to_publish → publishing → completed`.

Из `parsing`, `validating` и `publishing` worker восстанавливает просроченный
lease. Отмена до `publishing` является немедленной; во время `publishing` —
кооперативной. Терминальные состояния: `completed`, `failed`, `cancelled`.

- ranking URL changes;
- SERP features;
- конкурентов;

Проектная заметка запроса ограничена 4 000 символами. В табличной проекции
передаётся только признак её наличия, а текст читается в tenant-scoped карточке.
График позиций строится из append-only rank snapshots отдельно по tracking
context/search engine. Отсутствие позиции разрывает сплошную линию, выводится
на отдельной оси «нет» и соединяется с соседними замерами только пунктиром —
оно не подменяется нулём или предельной позицией. График остаётся видимым и
когда все доступные замеры имеют состояние `not found`: вместо пустого блока
он показывает сохранённые кресты на оси «нет». Наведение и клавиатурный
фокус притягиваются к ближайшему замеру и показывают позицию, точные дату и
время, поисковую систему и источник выдачи, provider, регион, устройство,
глубину и название tracking context. В таблице основное число является
текущей позицией, а рядом выводится изменение относительно предыдущей
найденной позиции: зелёное `▲N`, красное `▼N`, `—` без изменений или
«Новая». Если свежий замер не нашёл позицию, показывается `×` и «Была N».
Новые частотности и позиции появляются в открытой таблице через
reconciliation текущей HTTP-проекции по изменению progress, без перезагрузки
страницы; WebSocket не является источником истины.

## 27. Критерии производительности

- Открытие таблицы не должно загружать весь набор.
- p95 первого блока до 500 строк — не более 1,5 секунды при прогретом кеше.
- Фильтр по индексируемым полям — p95 не более 1 секунды.
- Scroll виртуализированной таблицы — целевые 60 fps на поддерживаемом устройстве.
- Inline update подтверждается UI не позднее 300 мс optimistic state; серверный p95 — до 500 мс.
- Импорт 5 ГБ принимается без HTTP timeout и продолжает обработку после закрытия вкладки.
- Bulk operation по миллионам строк не удерживает длинную HTTP-транзакцию.
