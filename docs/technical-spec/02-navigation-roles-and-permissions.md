# Навигация, роли и разрешения

## 1. Уровни интерфейса

Интерфейс разделяется на четыре контекста:

1. глобальный аккаунт пользователя;
2. рабочая область;
3. проект;
4. внутренняя администрация платформы.

Текущий контекст должен быть очевиден из заголовка, breadcrumbs и переключателя рабочей области/проекта.

## 2. Основная навигация приложения

### 2.1. Глобальное меню

- переключатель рабочей области;
- список и поиск проектов;
- глобальный поиск;
- очередь заданий;
- уведомления;
- быстрый запуск операции;
- профиль пользователя;
- язык и timezone;
- справка и поддержка.

Tenant switcher показывает для каждой рабочей области аватар с инициалами
канонического владельца. Области текущего владельца имеют подпись «Личный», а
чужие — имя и email владельца. Проекты показывают пользовательский logo либо
безопасно обнаруженный favicon сайта; недоступное, отсутствующее или
небезопасное изображение скрывается без broken-image и без влияния на выбор.
Рядом с проектом показывается ненулевое число его активных операций. Счётчик
строится только по доступным пользователю проектам и не раскрывает чужие ID.
Тот же переключатель находится рядом с заголовком семантики, операций, заметок
и карты страниц.

### 2.4. Адаптивная навигация

- При ширине менее 1024 px боковое меню сворачивается.
- При ширине менее 768 px показывается мобильная навигация с основными разделами: обзор, задачи, проблемы, отчёты, ещё.
- Полноценное редактирование таблицы семантики на мобильном не является обязательным.
- На мобильном должны поддерживаться просмотр, фильтры, комментарии, подтверждение операций и управление очередью.

## 3. Поиск и command palette

Комбинация `Ctrl/Cmd + K` открывает command palette.

Поиск должен находить:

- рабочие области;
- проекты;
- ключевые фразы;
- группы и кластеры;
- URL;
- конкурентов;
- задания;
- отчёты;
- заметки и файлы;
- участников.

Действия command palette:

- перейти в проект;
- добавить запросы;
- создать задание;
- открыть очередь;
- создать автоматизацию;
- пригласить пользователя;
- перейти к настройкам.

Результаты группируются по типу, поддерживают клавиатурную навигацию и учитывают права доступа.

## 4. Модель ролей

### 4.1. Роли платформы

Эти роли действуют только во внутренней административной панели:

- `PLATFORM_SUPER_ADMIN` — полный доступ, включая назначение platform-ролей;
- `PLATFORM_OPERATIONS` — задания, интеграции, состояние сервисов;
- `PLATFORM_SUPPORT` — поддержка и ограниченный support access;
- `PLATFORM_FINANCE` — платежи, счета, ledger, refunds;
- `PLATFORM_CONTENT` — маркетинговый контент и SEO metadata;
- `PLATFORM_SECURITY_AUDITOR` — аудит, сессии, события безопасности, без изменения данных;
- `PLATFORM_ANALYST` — агрегированная продуктовая аналитика без доступа к секретам.

`PLATFORM_SUPER_ADMIN` не должен использоваться как повседневная роль.

### 4.2. Роли рабочей области

- `OWNER`;
- `ADMIN`;
- `SEO_LEAD`;
- `SEO_SPECIALIST`;
- `ANALYST`;
- `CONTENT_EDITOR`;
- `CLIENT`;
- `VIEWER`;
- пользовательская роль (`CUSTOM`).

### 4.3. Владелец

- В рабочей области должен существовать хотя бы один владелец.
- Последний владелец не может покинуть рабочую область или снять с себя роль.
- Передача владения требует повторной аутентификации и подтверждения.

### 4.4. Пользовательские роли

Администратор может создать роль на основе шаблона и включить отдельные разрешения. Системные роли не редактируются; их можно клонировать.

### 5.6. Интеграции

- `integration.view`;
- `integration.connect`;
- `integration.update`;
- `integration.delete`;
- `integration.test`;
- `integration.view_usage`;
- `integration.use_system_credentials`;
- `integration.manage_fallback`;

Пользователь без специального разрешения никогда не видит полный секрет.

Project connector settings используют `integration.view` для чтения и
`integration.update` для создания/изменения binding. Системная роль и
project assignment пересекаются: `MANAGER` не расширяет более узкую
workspace role, а `VIEWER`/`MEMBER` сужают даже `OWNER`/`ADMIN` в рамках
назначения. В текущей системной матрице binding меняют `OWNER` и `ADMIN`;
`SEO_LEAD`/`SEO_SPECIALIST` могут видеть и тестировать доступные им credentials,
но не обходят отсутствие `integration.update`.

Billing `READ_ONLY` оставляет `integration.view`, но mutation guard возвращает
`402 PAYMENT_REQUIRED`. Архивный проект также читается, а изменение binding
возвращает `409 RESOURCE_STATE_CONFLICT`. Будущие platform credentials,
fallback и budgets дополнительно требуют соответственно
`integration.use_system_credentials`, `integration.manage_fallback` и
`billing.set_budgets`; наличие permission само по себе не включает ещё не
реализованную возможность.

## 7. Проектные назначения и исключения

- Членство задаётся на уровне рабочей области.
- Для каждого проекта участнику можно назначить доступ: `none`, `viewer`, `member`, `manager`, `custom`.
- Проектное назначение может только сужать разрешения рабочей области, кроме явного приглашения клиента в конкретный проект.
- Запрет имеет приоритет над разрешением.
- Разрешение проверяется сервером для каждого запроса и WebSocket-события.

## 8. Клиентский режим

Роль `CLIENT`:

- видит только разрешённые проекты;
- не видит API-ключи, внутренние расходы, черновые заметки и служебные комментарии;
- не видит внутренние задачи, отмеченные как private;
- может открывать опубликованные отчёты;
- может оставлять комментарии в разрешённых местах;
- может скачивать разрешённые экспорты;
- не может изменять исходные SEO-данные.

Интерфейс клиента должен быть упрощён и не содержать неактивных пунктов меню.

## 9. Гостевые ссылки

- Ссылка выдаётся на конкретный отчёт или dashboard view.
- Должна иметь срок действия.
- Может быть защищена паролем.
- Может разрешать или запрещать экспорт.
- Может ограничиваться списком email.
- Может быть отозвана немедленно.
- Открытия ссылки журналируются.
- Ссылка не даёт доступа к навигации приложения.

## 10. Support access

Сотрудник поддержки не должен входить под паролем пользователя.

Допускается временная support-сессия:

- только после выбора причины и номера обращения;
- с ограниченным сроком;
- с минимальным набором прав;
- с видимым баннером «Режим поддержки»;
- с обязательной записью всех действий;
- без отображения API-секретов и платёжных реквизитов;
- с возможностью запретить support access владельцем рабочей области.

## 11. Состояния доступа в UI

Для элемента, недоступного по роли, применяются правила:

- если сам факт существования функции чувствителен — элемент скрывается;
- если функция является частью тарифа — элемент показывается с объяснением ограничения;
- если нужна роль — элемент disabled с указанием требуемого разрешения;
- прямой URL возвращает страницу `403`, не `404`, если раскрытие существования ресурса допустимо;
- API возвращает стандартизированную ошибку `FORBIDDEN`;
- изменение прав в активной сессии применяется не позднее 60 секунд и немедленно для опасных операций.
