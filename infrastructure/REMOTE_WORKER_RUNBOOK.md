# Удалённый воркер через Gateway

Удалённые исполнители поддерживают позиции/выдачу, частотности, парсинг
Wordstat, ИИ-ответы, кластеризацию, обход сайта, разбор импорта, формирование
экспорта и антивирус. Права, подготовка данных, биллинг, контроль отмены и
пакетное сохранение остаются у существующих центральных владельцев данных.
Письма всегда отправляет основной сервер. SQL, Redis и ключи хранилища на
удалённые узлы не передаются; локальная копия базы не требуется.

Агенту не нужны входящий IP, PostgreSQL, Redis или копия базы. Он делает
исходящие HTTPS-запросы к центру: heartbeat раз в 10 секунд и один пакетный
опрос заданий раз в 5 секунд при простое **на сервер**, независимо от числа
слотов. После завершения работы следующая пачка запрашивается быстрее.
Ответ содержит задания разных типов в пределах свободных HTTP/CPU-слотов.
Разбор файлов и кодирование выполняются в отдельных worker threads, чтобы
не блокировать heartbeat и другие операции.

## Центр

На тестовом VPS публичный worker-маршрут доступен через
`https://144.31.221.28:3000/worker/v1/*`. Отдельный API listener `:4000`
может быть недоступен с удалённого сервера; для воркера используйте `:3000`.
Production Web проксирует только разрешённые `/worker/v1/*` POST в Jobs;
остальные пути, cookies и browser Origin туда не передаются. Для каждого
центра одновременно нужны:

```dotenv
WORKER_GATEWAY_ENABLED=true
JOBS_HTTP_INTEGRATION_CREDENTIAL_ROLE=BOTH
REMOTE_WORK_ENABLED=true
REMOTE_WORK_CONTROL_URL=http://127.0.0.1:4002
```

Production Frontend дополнительно получает `WORKER_GATEWAY_ENABLED=true` и
внутренний `WORKER_GATEWAY_INTERNAL_URL=http://backend-execution:4002` из
Compose. В тестовом VPS это `http://127.0.0.1:4002`. Флаг по умолчанию
выключен, пока Gateway не прошёл migration/readiness-проверку.

Их включают только после миграций и настройки Caddy `/worker/v1/*`;
при отсутствии флага HTTP-процесс не получает доступ к BYOK-ключам.
`BOTH` — осознанное ослабление изоляции HTTP-процесса, согласованное для
этого этапа. Не открывайте наружу порт Jobs `4002`, PostgreSQL или Redis.

## Регистрация узла

1. В админке откройте «Воркеры» → «Создать воркер». Выберите нужные
   операции, HTTP/CPU-пределы и индивидуальные ограничения. Новый узел
   выключен: для первой проверки связи не включайте его.
2. Скопируйте показанные **один раз** UUID узла и его токен. У каждого
   сервера — отдельный узел и отдельный токен. В админке можно сразу
   выключить или плавно остановить узел, а также перевыпустить его токен.
3. Токен задаётся в окружении **только удалённого воркера**. Не добавляйте
   его в Git, Docker image, URL, логи или конфигурацию главного сервера.
   Доступ к Environment в Dokploy и к Docker на узле оставьте доверенным
   администраторам: они могут прочитать переменные контейнера.

## Dokploy на удалённом сервере

Для всех возможностей используйте **Compose** с файлом
`infrastructure/worker.compose.yml`: рядом запускается ClamAV без публичных
портов. Если антивирус не нужен, допустим **Application** со stage
`remote-worker`; задайте `WORKER_INSPECTION_SLOTS=0`. В Dokploy выберите Git-источник,
`ker4ik13/seo-platform` и ветку `main` после production rollout; тестовый
стенд пока использует `codex/worker-fleet-db-pilot`.
Настройки сборки ([Build Type](https://docs.dokploy.com/docs/core/applications/build-type)):

| Поле Dokploy | Значение |
|---|---|
| Build Type | `Dockerfile` |
| Git Build Path | `/` |
| Docker Context Path | `.` (корень репозитория) |
| Dockerfile Path | `infrastructure/docker/backend.Dockerfile` |
| Docker Build Stage | `remote-worker` |
| Build Time Arguments | `PACKAGE_NAME=@seo-platform/backend-execution` |
| Replicas | `1` |

В Environment приложения задайте:

```dotenv
WORKER_CONTROL_URL=https://144.31.221.28:3000
WORKER_NODE_ID=<UUID_ИЗ_АДМИНКИ>
WORKER_NODE_TOKEN=<ТОКЕН_ИЗ_АДМИНКИ>
WORKER_HTTP_SLOTS=16
WORKER_RANK_SLOTS=0
WORKER_CPU_SLOTS=2
WORKER_WORDSTAT_SLOTS=10
WORKER_RESEARCH_SLOTS=10
WORKER_AI_ANSWER_SLOTS=5
WORKER_CLUSTERING_SLOTS=2
WORKER_CRAWL_SLOTS=8
WORKER_IMPORT_SLOTS=2
WORKER_EXPORT_SLOTS=2
WORKER_INSPECTION_SLOTS=0
WORKER_CPU_TASK_MEMORY_MB=1024
WORKER_HEARTBEAT_MS=10000
WORKER_LOG_QUERIES=false
```

Значение `WORKER_NODE_TOKEN` сохраните в Environment самого приложения
Dokploy, а не в репозитории. [Dokploy записывает переменные Compose в `.env`](https://docs.dokploy.com/docs/core/docker-compose);
доступ к ним и к Docker-инспекции равнозначен доступу к ключу воркера.
Если ключ станет известен посторонним, перевыпустите его в админке.
`WORKER_LOG_QUERIES=true` разрешает на доверенном узле кратко логировать
поисковые фразы; по умолчанию тексты и любые API-секреты не пишутся.
Слоты операций — верхние пределы: `WORKER_RANK_SLOTS` и остальные HTTP
capabilities не могут использовать больше `WORKER_HTTP_SLOTS`, а импорт,
экспорт и антивирус — больше `WORKER_CPU_SLOTS`. При большем значении агент
ограничивает его родительским пулом; остальные операции продолжают работать.
После сохранения Environment выполните Deploy/Redeploy и проверьте в логах,
что `worker <ID>` совпадает с активным узлом. Если Dokploy оставил старый ID,
проверьте состояние нового Swarm task: невалидные параметры могли завершить
его, после чего Swarm откатил прежний task.
Не настраивайте Domain или опубликованный порт: агент сам обращается к
центру исходящими HTTPS-запросами.

Для первого запуска оставьте узел выключенным в админке: появится heartbeat
без выдачи любых задач. После проверки связи включите узел в админке,
поставьте `WORKER_RANK_SLOTS=8` и сделайте Redeploy. В **Advanced →
Resources** для пробного узла можно поставить CPU Limit `4000000000`
(4 ядра) и Memory Limit `8589934592` (8 GiB); Dokploy требует именно
nanoCPU и байты, не `4` и не `8g`.
Для обновления работающего узла в Swarm выставьте **Stop Grace Period**
`3660000000000` (61 минута в наносекундах). Экспорт и антивирус могут
занимать до часа; старый агент не берёт новую работу после SIGTERM, но
подтверждает уже выданные задачи, пока новый обслуживает следующие. Убедитесь,
что у сервера хватает памяти на кратковременную работу двух контейнеров.
Центр делает один rank-проход не дольше пяти секунд в каждом пакетном `claim`.
Выданная provider-задача может начать платный запрос в течение 30 секунд
после постановки; позже она безопасно отказывается от HTTP-вызова.
Один agent запрашивает пачку раз в пять секунд при простое; после завершения
работы делает следующий запрос спустя минимум 100 мс. HTTP-слоты не
опрашивают центр по отдельности.
Wordstat резервирует RPS для всех выбранных типов фразы и до четырёх секунд
ждёт следующее окно XMLStock внутри уже полученной пачки. Это позволяет
использовать до десяти одновременных запросов физического ключа без повторной
постановки фраз в очередь.
Чтение `check/get` Арсенкин допускает до 30 секунд, а при потере ответа
воркера центр повторяет только чтение без нового платного `set`.
При единственном воркере короткое
ожидание свободных слотов во время обновления возможно; сохранённые ответы
и новые запросы продолжаются после heartbeat новой задачи.

Из сети удалённого сервера сначала проверьте TLS без `-k`:

```bash
curl -i -H 'Content-Type: application/json' -d '{}' \
  https://144.31.221.28:3000/worker/v1/heartbeat
```

Ожидается HTTP 400 без заголовков идентификации узла. Ошибка проверки сертификата, DNS или
соединения означает, что запускать узел пока нельзя.

## Обычный Docker Compose вне Dokploy

Скопируйте `infrastructure/.env.worker.example` в локальный
`infrastructure/.env.worker` и укажите `WORKER_NODE_ID`, `WORKER_NODE_TOKEN`
и `WORKER_CONTROL_URL`. Файл `.env.worker` должен оставаться вне Git и быть
доступен только администратору сервера. Для тестового VPS:

```dotenv
WORKER_CONTROL_URL=https://144.31.221.28:3000
WORKER_NODE_TOKEN=<ТОКЕН_ИЗ_АДМИНКИ>
WORKER_HTTP_SLOTS=16
WORKER_RANK_SLOTS=8
WORKER_CPU_SLOTS=2
WORKER_HEARTBEAT_MS=10000
WORKER_CONTAINER_CPUS=4.0
WORKER_CONTAINER_MEMORY=8g
```

`WORKER_RANK_SLOTS=0` отключает только позиции; другие операции имеют
собственные переменные. Для проверки связи держите узел выключенным, затем
включите его и выставьте нужные слоты. Новый узел сначала наследует `.env`;
ручные значения из админки заменяют их после следующего heartbeat. Лимит
физического XMLStock-ключа общий для всех серверов и рабочих областей.
Если нужен `WORKER_RANK_SLOTS=20`, задайте также `WORKER_HTTP_SLOTS=32`,
примените Environment новым Deploy/Redeploy и в админке узла выставьте
«HTTP-слоты» не меньше 20. Иначе действует меньший административный предел:
например, агент сообщает 20 rank/32 HTTP, но при admin cap 16 доступны
только 16 rank-слотов. Карточка узла показывает все три значения отдельно.

Из корня той же версии репозитория запустите:

```bash
docker compose --env-file infrastructure/.env.worker \
  -f infrastructure/worker.compose.yml up -d --build
docker compose --env-file infrastructure/.env.worker \
  -f infrastructure/worker.compose.yml ps
```

Для ручного Docker Compose берите ту же ветку, что развернута в центре.
Пошаговая установка на чистом Windows-ПК описана в
[`WINDOWS_WORKER.md`](./WINDOWS_WORKER.md). Не копируйте на узел `.env` главного сервера,
дампы, пользовательские файлы или главный runtime-каталог.

## Проверка и аварийное отключение

- В админке узел показывает связь, слоты и время heartbeat. «Подробнее»
  открывает ресурсы и назначения, «Настройки» — пределы всех возможностей.
  При нулевых rank-слотах позиции не выдаются; другие типы не блокируются.
- После включения 8 слотов запустите только заранее согласованный небольшой
  съём. Сравните прогресс операции и `docker compose ... logs` без вывода
  токенов или ключей. Потерянный узел освобождается по lease; для
  неоднозначного платного запроса допускается не более одного автоповтора.
- Для остановки новых задач нажмите «Остановить плавно». Для немедленного
  запрета новых задач — «Выключить». Уже выданные задания могут закончить
  запрос и отправить результат; после обрыва lease работу восстановит центр.
- Выключение, плавная остановка и удаление требуют подтверждения. «Удалить
  воркер» скрывает регистрацию и отзывает токен, но не удаляет результаты и
  историю. Контейнер на удалённой машине оператор останавливает отдельно.
  Для повторного подключения удалённого узла создайте новую регистрацию.

XMLStock rank poll теперь закрепляется за одним здоровым узлом на всю
операцию: занятость его слотов не заставляет основной сервер перехватывать
страницы. Настройте `WORKER_RANK_SLOTS` и admin cap на достаточное число
HTTP-слотов; внутри узла операции делят эти слоты и общие лимиты физического
ключа. Назначенный узел виден в админке и между активными GET.
Disable/drain, нулевая capacity либо heartbeat старше 30 секунд переключают
операцию на другой узел, а при отсутствии узлов — на основной сервер.
Текущие page leases сначала дожидаются результата либо expiry.
Провайдерские HTTP-этапы других операций также делегируются через Gateway.
Общий лимит `XMLSTOCK_HTTP_GLOBAL_CONCURRENCY=64` относится к основному
серверу, а `WORKER_HTTP_SLOTS` — к конкретному узлу. Ограничение физического
ключа (например, 10 Yandex Live) не умножается от добавления серверов.
Настройки слотов — верхние пределы, не обязательная постоянная нагрузка.
В очередь попадают только подготовленные этапы действующих операций.
Крупные провайдерские HTTP-входы (свыше 896 КиБ) сохраняют существующее
локальное исполнение: они не записываются большим JSON в PostgreSQL и не
получают ошибку из-за лимита транспортного конверта. Это ограничение
переноса HTTP-этапа, не новый лимит количества запросов операции.
Файлы импорта/экспорта и крупные ответы передаются через хранилище.

Крупные входы и результаты передаются подписанными URL конкретных объектов.
Успешный ACK означает, что результат принят в центре; последующий owning
workflow сохраняет его в основной доменной БД. Незавершённый запрос после
потери узла восстанавливается по существующей политике операции. Транспорт
не повторяет платный вызов самостоятельно; два неоднозначных исполнения
одного платного запроса блокируют третье и требуют внимания.

Офисному серверу не нужен входящий порт или домен. Не отключайте проверку TLS.
Для антивируса в отдельном Application нужен доступный из контейнера clamd:
`WORKER_MALWARE_SCANNER_HOST`, `WORKER_MALWARE_SCANNER_PORT=3310`.
В worker Compose эти значения заданы автоматически. SMTP-секреты на узле
не нужны. Для 10–100 одновременных операций требуется отдельный нагрузочный
замер; число подключённых серверов само по себе не доказывает такую ёмкость.
